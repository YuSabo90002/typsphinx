## Checklist

Each item names its Owner and its Ordering dependency on the items before it.

### 1. Open the pull request and merge it to `main`

**Owner:** `/gsd-complete-milestone`.
**Ordering:** first — every item below depends on the milestone branch (`gsd/v0.7.1-bug-fix-round`)
reaching `main`. Note that `origin/main` has already moved once during this phase (D-20 merged
`9b2b76b` — the v0.7.0 release plus PR #131 — into the milestone branch), so this PR's diff against
`main` reflects only the milestone's own contribution on top of that already-merged content, not a
double-count of PR #131.

### 2. Push the `v0.7.1` tag on the merge commit

**Owner:** `/gsd-complete-milestone`.
**Ordering:** after item 1 (the tag should point at the merged `main`, not the pre-merge branch).
Pushing `v0.7.1` fires `.github/workflows/release.yml`. The `validate` job will fail fast if
`CHANGELOG.md` has no usable `## [0.7.1]` section — which it does, per SC#2's own measurement in
`46-RELEASE-EVIDENCE.md` (the heading is present, non-empty, and the extractor's real hand-run
against it in `46-REL04-EVIDENCE.md` exits 0 with the curated section on stdout).

### 3. Let `release.yml` run to completion: `validate` → `build` → `publish-pypi` → `create-release`

**Owner:** `/gsd-complete-milestone`, with a human approval step on the `pypi` environment.
**Ordering:** after item 2.
**Watch `create-release` succeed and record the run id — this is the step that closes REL-04.**
Note the v0.7.0 precedent: run `30848860064`'s `create-release` failed at `uv: command not found`
(exit 127, the `astral-sh/setup-uv` step was missing), the workflow was fixed on `main` afterwards
(the `Install uv` / `Set up Python` steps now sit ahead of the `Generate release notes` step, lines
162-168 of `release.yml`, confirmed present and undisturbed in `46-REL04-EVIDENCE.md` §
"Precondition 1"), and the fix has never been exercised end to end — no real tag push has run this
workflow file since the fix landed. Note also that `publish-pypi` waits on owner approval of the
`pypi` environment, the same gate every prior release in this project's history has exercised.

### 4. Advance the `typsphinx-doc-translations` submodule pin and push a matching `v0.7.1` tag there

**Owner:** `/gsd-complete-milestone` plus human.
**Ordering:** after item 1 (the translations-repo tag should point at content matching the merged
`main`; it does not need to wait for item 3's PyPI/GitHub Release publish, only for the merge).
This is the standing two-repository tagging cost adopted at v0.6.4 and carried through v0.6.5 and
v0.7.0 (`STATE.md` § "Shipped Milestone (v0.7.0 — archived)": pin advanced to `75fd8ed` by
`update-pin.yml` run `30848873442`, tagged `v0.7.0` there). **D-13's correction, recorded here so
nobody looks for work that does not exist:** the `typsphinx-doc-translations` repository contains
no `conf.py` and no `.typ` template (`46-GREEN-TREE-EVIDENCE.md` § "D-13 note" confirmed this
directly) — it is a pure `.po`/RTD-translation-project repository. There is therefore **nothing to
remove or edit in it**; the only action is advancing the submodule pin and pushing the matching
`v0.7.1` tag, exactly as the v0.6.4/v0.6.5/v0.7.0 precedent already did.

## Not done in this phase, by design

This phase (and no plan within it) performed any of the following. The scope fence is absolute —
every one of these belongs to `/gsd-complete-milestone` or to the owner, never to a prep-only
release phase:

- No `git tag v0.7.1` (or any tag) was created, locally or on the remote.
- No release workflow (`release.yml`) was triggered or executed as a real workflow run — every
  claim about its behaviour in this phase's evidence is either a direct hand-run of the script it
  calls, or a static read of its YAML structure (`46-REL04-EVIDENCE.md`).
- Nothing was published to PyPI.
- No GitHub Release was created.
- No pull request was opened or merged by this phase (D-20's merge pulled `origin/main` *into* the
  milestone branch — the inbound direction — not the reverse).
- No Read the Docs setting was changed — Default Version, Default branch, or otherwise.
- No `.planning/REQUIREMENTS.md` checkbox or Traceability row was flipped — `git diff --name-only --
  .planning/REQUIREMENTS.md` is empty over every commit in this phase.

**D-03's declined fail-loud shim for the removed `typst_authors`:** the silent-loss failure mode is
real and measured — a `conf.py` still setting the removed `typst_authors` gets no error, just a
silently-ignored config value — and was deliberately declined for this milestone (D-03), consistent
with the prep-only fence's own reasoning: adding a `typsphinx/` shim here would be exactly the kind
of code change this phase's scope excludes.

**D-27's two `TypstBuilder._track_image()` defects ship in v0.7.1 unfixed**, named by their record
filenames:

- `.planning/todos/pending/2026-08-10-rehomed-converted-image-collides-with-srcdir-images-dir.md`
  (major) — a converted image rehomed to `images/<basename>` collides with an ordinary source image
  genuinely at `<srcdir>/images/<basename>`; one is silently never copied, the other document
  renders the wrong picture, no warning. A regression in failure mode: pre-PR the same project
  aborted the build loudly.
- `.planning/todos/pending/2026-08-10-track-image-rehome-escapes-outdir-for-non-doctreedir-abs-uri.md`
  (minor) — `relpath(uri, doctreedir)` returns `../`-prefixed paths for an absolute URI outside
  `doctreedir`, so `copy_image_files()` writes outside `outdir`.

Both records stay in `todos/pending/` (confirmed by this plan's Task 3). **No `### Known
Limitations` CHANGELOG section was added and no GitHub issue was filed** — the full counter-case
(regression in failure mode, non-exotic reachability, silent wrong output being the failure class
this project's core value names directly, the `### Known Limitations` precedent at
`CHANGELOG.md:817`, and an otherwise-empty public issue tracker) was argued in full and declined by
owner decision (D-27). Fixing them in Phase 46 was also rejected on consistency grounds — it would
contradict D-03's own reasoning for holding the prep-only fence.

**The stale module docstring in `scripts/extract_changelog_section.py`** (lines 24, 32) states that
`CHANGELOG.md` carries two `## [Unreleased]` headings; a direct count
(`grep -c '^## \[Unreleased\]' CHANGELOG.md`) returns one — the tail block's `[Unreleased]:` line is
a markdown link definition, not a heading, and `### Planned for Future Releases` is a subsection
under the one heading, not a second heading of its own. Left unedited because this phase permits
exactly two non-planning code edits (D-22's Windows repair and the `RELEASE_VERSIONS` append in
`tests/test_changelog_page_gate.py`), and correcting a stale docstring is not one of them. The
script's algorithm is purely positional and is correct either way — only its docstring's headcount
claim is stale. This observation carries `docs/source/changelog.rst`'s now-narrower
`EXCLUDED_CLAIM_PAGES` reason string, which the D-09 migration section outgrew (per
`46-CI-EVIDENCE.md` § "Observation carried forward").
