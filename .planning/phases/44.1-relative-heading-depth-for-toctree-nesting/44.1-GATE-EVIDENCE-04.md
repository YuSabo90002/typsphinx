## 3. SC#3(a) result — resolved-level invariance

**The one interpretive decision SC#3(a) forces, recorded rather than applied silently:** `typst
.query` follows Typst's `include()`, so querying a master with a toctree necessarily returns its
children's headings too — exactly what this phase moves. Read literally over the *composed*
document, "identical level sequence before and after" cannot hold (and is not expected to: the
composed sequence for the docs-corpus master changes at 150 of its 156 positions, per § 3's A2
below). The satisfiable reading — SC#3's own next sentence in ROADMAP.md, "the master renders at
offset: 0, so depth == level there" — is that the **master's own** headings are invariant. Both
readings are discharged and recorded, per this plan's own instruction; A1 is the pass/fail
criterion, A2 is the evidence that A1 is not invariance-by-nothing-happening.

### A1 — the master's own headings, isolated by stubbing

**Stubbing transform, applied identically to both sides:** copy the build output tree; for every
`.typ` file EXCEPT the master and `_template.typ`, truncate to empty (`write_text("",
encoding="utf-8")`); query the (now-stubbed) master.

**`_template.typ` is deliberately excluded from stubbing** — an interpretive decision recorded
here rather than applied silently. The master reaches it via `#import "_template.typ": project`
(a Typst **import**, needed to define the `project()` function the master's own `#show:
project.with(...)` show rule calls in order to compile AT ALL), not via toctree `#include()` — the
composition mechanism this phase's fix actually changes. Emptying it would remove the `project`
symbol the import statement names and abort compilation with an unresolved-import error, which is
not "isolate the master's own heading sites," it is "make the master fail to build." Every file
reached by an actual `include(...)` call (confirmed by `grep -n 'include(' <master>.typ`) IS
stubbed.

**Docs corpus** (`typsphinx.typ`, has a toctree — 10 direct `include()` calls confirmed by grep:
`installation.typ`, `quickstart.typ`, `user_guide/index.typ`, `user_guide/configuration.typ`,
`user_guide/builders.typ`, `user_guide/templates.typ`, `examples/index.typ`, `api/index.typ`,
`contributing.typ`, `changelog.typ` — plus 2 more nested one level deeper inside
`examples/index.typ`'s own toctree: `examples/basic.typ`, `examples/advanced.typ`; **12 files
stubbed**, matching the 12-non-master-non-template count exactly):

| side | stubbed levels | stubbed `(level, title)` outline |
|---|---|---|
| pre-fix  | `[1, 1, 1, 2, 2, 1]` | `(1,''), (1,'Contents'), (1,'typsphinx Documentation'), (2,'Key Features'), (2,'Quick Links'), (1,'Indices and tables')` |
| post-fix | `[1, 1, 1, 2, 2, 1]` | *identical* |

**Identical: yes.**

**test-basic corpus** (`output.typ`, **no toctree at all** — confirmed: 0 `include()` calls; A1
stubbing truncates zero files, since the only other `.typ` in the build is `_template.typ`, which
is excluded by the rule above):

| side | stubbed (== un-stubbed, since nothing was truncated) levels |
|---|---|
| pre-fix  | `[1, 1, 1, 2]` |
| post-fix | `[1, 1, 1, 2]` |

**Identical: yes.** Because test-basic's master has no toctree, A1 and the "un-stubbed full-document
comparison" required for no-toctree masters are the SAME measurement here — recorded explicitly:
this is the literal reading of SC#3(a) holding directly, with no interpretive gap, for the one
corpus master that has no toctree.

**A1 verdict: both masters (the one with a toctree and the one without) show an identical resolved
level sequence for their own headings, before and after the fix.**

### A2 — the composed delta, and its per-heading depth accounting

Un-stubbed, full-document queries of both masters, both sides (test-basic: identical to A1, already
shown above; docs corpus, the interesting case):

**Docs corpus, composed:** `156` headings on both sides (same count — pure level-only diff, not a
content/order diff, confirmed below). Full `(level, title)` outlines recorded via
`typst.query(...)` with NO stubbing — see the per-heading accounting table immediately below; the
raw outlines are long (156 rows) and are not reproduced verbatim a second time here, since the
accounting table subsumes them (it carries every row's pre-level, post-level, and delta).

**Per-heading accounting, using each heading's Typst `<label>`** (e.g. `<installation:next-steps>`
vs `<examples_u2f_basic:next-steps>`) to classify UNAMBIGUOUSLY by source document — plain
title-text matching was tried first and produced 5 false "mismatches" purely from generic section
titles ("Next Steps", "See Also") that are reused, with distinct labels, across multiple documents
(confirmed by `grep -n '"Next Steps"\|"See Also"' <all .typ files> | grep 'heading('`: both
strings genuinely appear in more than one document). The label's docname prefix removes the
ambiguity:

```
uv run python3 <script importing typst directly, querying both masters full,
                classifying every heading by its label's docname prefix,
                comparing (post_level - pre_level) against an expected depth
                derived structurally: 0 for the master's own headings (docname
                "index" or no label), 2 for headings labeled under
                "examples_u2f_basic" or "examples_u2f_advanced" (confirmed via
                grep to have zero further nested include() calls of their own),
                1 for every other docname>
```

**Result:**
```
Total headings: 156
Mismatches: 0

Distinct docnames seen, with assigned depth:
  (no-label): depth=0
  api_u2f_index: depth=1
  changelog: depth=1
  contributing: depth=1
  examples_u2f_advanced: depth=2
  examples_u2f_basic: depth=2
  examples_u2f_index: depth=1
  index: depth=0
  installation: depth=1
  quickstart: depth=1
  user_guide_u2f_builders: depth=1
  user_guide_u2f_configuration: depth=1
  user_guide_u2f_index: depth=1
  user_guide_u2f_templates: depth=1

Counts by expected_depth: {0: 6, 1: 128, 2: 22}
```

**All 156 of 156 headings account for exactly `post_level - pre_level == include_depth`, where
`include_depth` is the number of nested toctree `context { set heading(offset: heading.offset +
1) }` scopes the heading's own document sits inside** — 6 headings at depth 0 (the master's own,
matching A1 exactly), 128 at depth 1 (direct toctree children of the master), 22 at depth 2
(`examples/basic.typ` and `examples/advanced.typ`'s own headings, reached through TWO nested
scopes: master's own toctree wrapping `examples/index.typ`, and `examples/index.typ`'s own nested
toctree wrapping `basic.typ`/`advanced.typ`). This is D-07's accumulation claim, now proven not
just on the 8-heading `integration_nested_toctree` fixture (plan 01's own gate) but across the
full, real 156-heading `docs/source` corpus.

**Title-sequence check (confirms A2 is a pure level-only diff, not a content/reordering diff):**
`pre_titles == post_titles` (positional list equality over all 156 titles) → **True**.

**A2 is not a pass/fail criterion** (per the plan's own framing) — it is the evidence that A1's
zero-diff is not vacuous: every one of the 150 headings that DID move, moved by exactly its
document's own nesting depth, accounted for individually, not merely "some things changed."
