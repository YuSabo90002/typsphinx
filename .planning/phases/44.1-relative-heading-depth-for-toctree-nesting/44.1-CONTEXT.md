# Phase 44.1: Relative Heading Depth for Toctree Nesting - Context

**Gathered:** 2026-08-04
**Revised:** 2026-08-05 — SC#2 resolved to option-a; the "nested scopes accumulate" premise this
document previously asserted was falsified by measurement and is corrected below (D-07).
**Status:** Ready for planning

<domain>
## Phase Boundary

Make a document reached through a `toctree` render its headings one level deeper than its parent, so
the PDF outline nests instead of being flat. One requirement: **TOC-01**.

The repair has **two** parts. The first was locked by ROADMAP.md / REQUIREMENTS.md before this
discussion; the second was added on 2026-08-05 by owner decision D-07 after the first was measured
to be insufficient for SC#2.

1. **`visit_title` emits `depth:` instead of `level:`.** In Typst `level:` is the final absolute
   level and overrides the ambient `set heading(offset: …)`, so the `offset: 1` that `visit_toctree`
   wraps its `include()` calls in (`translator.py:4762`) is inert. Only `depth:` is relative
   (`offset + depth`).

2. **`visit_toctree` emits a context-relative offset increment instead of an absolute one.**
   `set heading(offset: N)` is an absolute assignment on Typst's style chain, not an increment, so a
   nested scope *replaces* its parent's offset rather than adding to it. Without this second change
   nested toctrees do not compose and SC#2 is unsatisfiable.

Re-verified during this discussion against the pinned typst-py 0.15.0, not taken on trust:

```
set heading(offset: 2)
heading(level: 1, …)  → typst.query(…, 'heading', field='level') → 1   (offset ignored)
heading(depth: 1, …)  → 3                                             (offset + depth)

three nesting levels, absolute `set heading(offset: 1)`            → [1, 2, 2]   (replaced)
three nesting levels, `context { set heading(offset: heading.offset + 1) }` → [1, 2, 3]   (accumulated)
```

**Not in this phase:**
- The `outline(depth: …)` mapping in the master template (D-03 below — treated as a template-level
  concern, deferred with its measurements).
- Anything about `typst_documents` derivation (Phase 44, shipped).
- The README / changelog documentation work (Phase 45).
- **The multi-master composition defects found on 2026-08-05** (a shared document silently dropped
  across masters; a master that is also a toctree child failing to compile, and re-expanding the
  template mid-body if it did). These are independent of TOC-01, reproduce on the *unfixed* code,
  and are recorded in `<deferred>` with their measurements.

## Implementation Decisions

### SC#2 — nested toctree composition

- **D-07: `visit_toctree` emits a context-relative heading-offset increment (option-a).** Owner
  decision, 2026-08-05. This supersedes the earlier statement in this document that `visit_toctree`
  "is NOT changed — it merely becomes effective for the first time" and that "nested toctree scopes
  then accumulate". That statement was a prediction carried over from the source todo and was
  **never verified**; measurement falsified it (see `<specifics>` items 7-8). Under the part-1 repair
  alone the grandchild in `tests/fixtures/integration_nested_toctree` resolves at 2, not 3, so SC#2
  as written in ROADMAP.md would be unmet.

  The emitted shape below was verified end to end — it compiles, and `typst.query` returns the
  accumulating sequence — against a real multi-document `sphinx-build -b typst` output, not only
  against a hand-written Typst snippet:

  ```typst
  context {
    set heading(offset: heading.offset + 1)
    include("mid.typ")
  }
  ```

  Rationale for choosing option-a over re-scoping SC#2 (option-b): the defect this phase exists to
  close is that the PDF outline is flat where the HTML and LaTeX hierarchies are nested. Option-b
  would fix that for exactly one level of toctree and leave it broken at two, i.e. ship a partial fix
  for the defect. The additional cost is one emitted expression, two docstring lines, and two test
  assertions — measured, see D-04's addendum.

  A second, independent argument surfaced during the discussion and is recorded because it is the
  stronger one: **an included document's `.typ` is a single shared file, and with an absolute offset
  there is no value it can carry that is correct for every master that includes it.** Measured on a
  two-master project where `shared` is included at depth 1 from master A and at depth 2 (via `mid`)
  from master B:

  | form | master A | master B |
  |---|---|---|
  | absolute `offset: 1` | `Shared Doc` → 2 ✓ | `Mid Doc` → 2, `Shared Doc` → **2** ✗ (collapsed) |
  | relative increment | `Shared Doc` → 2 ✓ | `Mid Doc` → 2, `Shared Doc` → **3** ✓ |

  The absolute form bakes a constant into a file whose correct value differs per include site. The
  relative form stores an *expression* evaluated at layout time, so no single value has to be chosen
  and the question of uniqueness disappears. This is why option-a is not merely the more complete fix
  but the only form that is well-defined at all once more than one include path exists.
  — **Reversibility:** reversible — one emitted expression in one method.

  (D-06 is deliberately unused in this phase: `typsphinx/translator.py:797-799` carries a pre-existing
  `# D-06:` marker from an earlier phase, whose stated rationale SC#4 requires superseding. Reusing
  the number here would make that supersession ambiguous.)

### SC#3 — proving master documents are unchanged

- **D-01: ROADMAP.md's SC#3 text must be rewritten before planning.** The clause "byte-identical
  `.typ` for every master document" is unsatisfiable under the locked repair. Measured: master
  documents emit the same heading call as included ones, so the `level:` → `depth:` substitution
  lands in master output too. `docs/_build/pdf/typsphinx.typ` carries four of them (lines 23, 30,
  86, 140), e.g.
  `[#heading(level: 1, {text("typsphinx Documentation")}) <index:typsphinx-documentation>]`. What is
  invariant is the *resolved level* (master renders at `offset: 0`, so `depth == level`), not the
  byte sequence. Owner decision: edit the SC#3 wording in ROADMAP.md rather than leaving it to be
  superseded implicitly, because `gsd-verifier` reads the ROADMAP SC text directly and would return
  NOT-MET against an unsatisfiable criterion. **Done** — commit `a16deee`.
  — **Reversibility:** reversible — planning-document text.

- **D-02: The SC#3 evidence stacks both proofs.** (a) *Resolved-level invariance* — compile each
  master before and after and assert the `typst.query(…, 'heading', field='level')` sequence is
  identical. (b) *Normalized byte invariance* — apply the mechanical substitutions to the pre-fix
  `.typ` files, then diff against post-fix and assert zero remaining difference. (a) shows the
  rendering does not move; (b) shows the change did not leak anywhere beyond the two emitted forms.
  Neither alone is sufficient: (a) would miss a non-heading diff, (b) would not show that the
  substituted text still resolves the same.
  — **Reversibility:** reversible — evidence-gathering scope.

  **Addendum, 2026-08-05 (D-07):** under option-a the normalization in (b) covers **two** mechanical
  substitutions, not one — the heading call's named argument *and* the toctree scope opener. The
  substitution set must be derived from the actual `git diff <pre>..<post> -- typsphinx/`, not
  assumed, or an over-broad substitution could manufacture an empty diff.

  Corpus is small, measured: `tests/roots/` contains exactly **one** root (`test-basic`), and
  `docs/source` contains **13** `.rst` files. No scope negotiation was needed.

## Specific Ideas

Everything below was measured against the repo venv (Sphinx 9.1.0, typst-py 0.15.0). It is evidence
the researcher should build on, not re-derive — but every figure transcribed into an assertion must
be re-taken first.

**1. `level:` vs `depth:` under an ambient offset, re-verified.** A two-heading document under
`set heading(offset: 2)` queried with `typst.query(…, 'heading', field='level')` returns `[1, 3]` —
`level: 1` stays 1, `depth: 1` resolves to 3.

**2. The current docs corpus, showing exactly what shifts.** From the committed build output:

| file | role | emitted today | resolves to after part 1 |
|---|---|---|---|
| `docs/_build/pdf/typsphinx.typ:23,30,86,140` | master | `level: 1`, `level: 2`, `level: 2`, `level: 1` | 1, 2, 2, 1 (unchanged, `offset: 0`) |
| `docs/_build/pdf/quickstart.typ:12,16,79,126,152` | included (offset 1) | `level: 1`, then four `level: 2` | 2, then 3 |
| `docs/_build/pdf/user_guide/index.typ:12,20,41` | included, and itself contains `set heading(offset: 1)` at `:17` | `level: 1`, `level: 2`, `level: 2` | 2, 3, 3 |

**3. Master output is not byte-invariant** — see D-01. The four master heading sites above are the
proof.

**4. Test-assertion census** (excluding `docs/_build/`, which is build output): 13 occurrences of the
literal `heading(level:` across 4 files — `tests/test_topics.py` 8, `tests/test_translator.py` 3,
`tests/test_pdf_render_gate.py` 1, `tests/fixtures/desc_rubric_decoupling_render_gate/golden.typ` 1.
Of these, 2 are inside one docstring (`test_topics.py:161-162`), giving the 12 edit sites of D-04.
Separately, `grep -rn 'heading(offset' typsphinx/` returns 3 sites and
`tests/test_toctree_requirement13.py` carries 2 assertion sites over the same literal (D-04 addendum).

**5. `typst.query` has zero existing uses in `tests/`** — all existing render gates end in pypdf
text extraction. The resolved-level check is a new technique for this suite.

**6. CI runs everything** — `.github/workflows/ci.yml` invokes `uv run tox -e <env>`, and
`tox.ini:22-23` runs `pytest {posargs:tests/}` with no `-m` filter. `pyproject.toml` registers the
`slow` marker but `addopts` is only `-v --strict-markers`.

**7. `set heading(offset: N)` does not accumulate (2026-08-05).** A document with a heading at
depth 1, then a scope opening `set heading(offset: 1)` containing a heading at depth 1, then a
further nested scope doing the same, queries as `[1, 2, 2]`. Written as
`context { set heading(offset: heading.offset + 1); … }` it queries as `[1, 2, 3]`.

**8. Item 7 holds through real `include()` calls, on real build output (2026-08-05).** Applying both
substitutions to the already-built `.typ` output of `tests/fixtures/integration_nested_toctree` in a
scratch copy and querying the master gives
`[1, 1, 1, 2, 3, 4, 3, 4]` for
`(template caption, Contents, "Nested Toctree Test", "Chapter 1", "Section 1",
"Content of section 1", "Section 2", "Content of section 2")` — SC#1 and SC#2 met together. With
part 1 alone the same sequence is `[1, 1, 1, 2, 2, 3, 2, 3]`: "Section 1" stuck at 2.

**9. The asymmetric-depth proof that the absolute form is not merely incomplete but ill-defined
(2026-08-05).** Two masters, `shared` included at depth 1 from A and at depth 2 (via `mid`) from B —
one `shared.typ` on disk:

```
ABSOLUTE  amaster [1 'Master A Title', 2 'Shared Doc', 3 'Shared Sub']
          bmaster [1 'Master B Title', 2 'Mid Doc',    2 'Shared Doc', 3 'Shared Sub']   ← collapsed
RELATIVE  amaster [1 'Master A Title', 2 'Shared Doc', 3 'Shared Sub']
          bmaster [1 'Master B Title', 2 'Mid Doc',    3 'Shared Doc', 4 'Shared Sub']   ← correct
```

The relative form stores an expression rather than a value, so the same file resolves differently and
correctly per include site. This is the load-bearing argument for D-07.

**10. The verified emitted shape** (from a real build, after substitution):

```typst
#{
[#heading(depth: 1, {text("Mid Doc")}) <mid:mid-doc>]

context {
  set heading(offset: heading.offset + 1)
  include("shared.typ")
}


}
```

Note the `context` keyword is emitted in code mode inside the surrounding `#{ … }` block and
compiles there; the block's contents are otherwise unchanged.

  `builder.py:99` declares `self._included_docnames` and `builder.py:420` resets it **once per
  `write()`**, but `write()` (`builder.py:432`) iterates `sorted(docnames)` a single time with no
  per-master pass. `visit_toctree` (`translator.py:4776-4785`) dedups against that one ledger, so the
  ledger spans the whole build rather than one master. Minimal repro — masters `index` and `bmaster`,
  both with a toctree listing `shared`:

  ```typst
  // bmaster.typ  (written first: sorted order)     // index.typ  (written second)
  { set heading(offset: 1)                          { set heading(offset: 1)
    include("shared.typ") }                         }        ← no include at all
  ```

  Master A's PDF loses `shared` entirely. **No warning is emitted.** Which master loses content is
  decided by docname sort order. The ledger's purpose (preventing duplicate Typst labels from a
  doubly-`include()`d file) is sound; the reset scope is wrong.

- **B-1 — a master that is also another master's toctree child does not compile.** With
  `typst_documents = [("index", "index", …), ("guide/index", "guide_master", …)]` and `index.rst`
  toctree-ing `guide/index`, the parent emits `include("guide/index.typ")` but `_resolve_output_stem`
  writes the file as `guide/guide_master.typ`. Measured:
  `RuntimeError: failed to compile document: file not found (searched at …/out/guide/index.typ)`.
  A loud failure, so lower severity than A.

- **B-2 — even with the filename reconciled, including a master re-expands the template mid-body.**
  Worked around B-1 by copying the file to the expected name and querying the root master:

  ```
  index.typ [1 ·, 1 'Contents', 1 'Root Master Title',
             2 ·, 2 'Contents', 2 'Guide Master Title',   ← second title page + second #outline()
             3 'Page One', 4 'Sub of page one', 3 'Shared Doc', 4 'Shared sub',
             2 'Shared Doc', 3 'Shared sub']              ← and a duplicate of shared
  ```

  Heading levels nest correctly, so this is not an offset problem. `writer.py`'s
  `_is_master_document()` treats "master" and "included" as an exclusive binary, and the state
  "master that is also a child" has no representation: one file would have to be simultaneously a
  self-contained document (template applied) and a body fragment (no template).

- **Architectural question this raises: is per-source-file `.typ` output + Typst `#include()`
  composition the right model at all?** Sphinx's LaTeX builder does the opposite and composes at the
  **doctree** layer: `sphinx/builders/latex/__init__.py:299` `write_documents()` loops over
  `document_data` (the `latex_documents` analogue) **per master**, calls `assemble_doctree()` (`:369`)
  which runs `inline_all_toctrees(...)` to fold the whole toctree closure into one doctree, then
  `env.resolve_references(largetree, indexfile, self)` on the folded tree, and finally walks the
  translator **once per master** to produce one `.tex` per master. There is no `\include`-level
  composition. typsphinx deliberately departs from this: `builder.py:391-397` documents that `write()`
  is overridden to use `env.get_doctree()` instead of `env.get_and_resolve_doctree()` specifically to
  preserve toctree nodes for `#include()` translation.

  Defects A, B-1, B-2 and TOC-01 itself are all consequences of that departure — a `.typ` file is
  shared across masters and must therefore be correct in several contexts at once, which only works
  for quantities Typst can express relatively. Heading depth happens to be one (`depth:`, and the
  relative offset of D-07). Template application, label uniqueness and numbering origin are not, and
  each already has a bespoke workaround in the codebase (`_is_master_document`,
  `_included_docnames`, `master_included_docnames` reference degradation, per-file `@preview` import
  re-declaration).

  Moving composition to the doctree layer would remove `offset` and relative `depth` from the design
  entirely (levels become computable in Python), make the dedup ledger and reference degradation
  per-master by construction, and dissolve the master/included binary. It would also **break the
  `-b typst` output contract** — the source-mirroring `.typ` tree is a user-visible feature — and
  change incremental-build granularity to per-master. This is a v0.8.0-class decision, not a patch
  release, and needs its own ADR-equivalent record; no ADR directory exists in this repo yet.

### Outline depth

- **`outline(depth: …)` does not track the toctree hierarchy the way LaTeX does.** Out of scope per
  D-03; recorded here with its measurements so whoever picks it up does not have to redo them.

  Measured in Sphinx 9.1.0: `sphinx/builders/latex/__init__.py:313-316` takes the master's first
  toctree `:maxdepth:` into `doctree['tocdepth']`; `sphinx/writers/latex.py:448` emits
  `\setcounter{tocdepth}{document['tocdepth'] + top_sectionlevel - 2}`. For the default `manual`
  theme, `latex_toplevel_sectioning` is unset so `top_sectionlevel = 1` and `sectionnames` is the
  full 7-element `LATEXSECTIONNAMES`, so the `+1` branch at `:451-453` does not fire — i.e.
  **`tocdepth = maxdepth - 1`**. In LaTeX's absolute units (chapter 0, section 1, subsection 2) that
  means `:maxdepth: N` shows exactly N levels *starting at the toctree'd document's title*, with the
  master's own title on the title page and outside the count.

  typsphinx differs structurally: the master's own title is emitted into the body as a level-1
  heading (`docs/_build/pdf/typsphinx.typ:23`) *in addition to* the template's title page
  (`templates/base.typ:67-74`). So after this phase, an included document's title sits at level 2 and
  its sections at level 3, and the LaTeX-equivalent expression is `outline(depth: maxdepth + 1)`.
  With today's `outline(depth: toctree_maxdepth)` and `maxdepth: 2`, the rendered TOC will show
  included document titles but not their sections. The current mapping only looked correct because
  the flat headings cancelled the error out. **Under D-07 this understates the gap**: with
  accumulation a grandchild's sections reach level 4, so more of the hierarchy falls outside a
  default-depth outline than this analysis assumed.

  Three implementation routes were measured, if it is ever taken up: change the expression inside
  `templates/base.typ:84-87` (nothing else changes, master `.typ` untouched, custom templates
  unaffected and unfixed); change the value `template_engine.extract_toctree_options()` passes
  (`template_engine.py:548-553`, which also maps `:maxdepth: -1` → `None`) so custom templates get it
  too, at the cost of the variable no longer meaning `:maxdepth:` and of a one-line diff in every
  master `.typ`; or add a new template parameter, which is the breaking option — see the next item.

- **The documented custom-template contract is wrong, and the documented example does not compile.**
  Found while evaluating the previous item; unrelated to TOC-01 and out of scope here.
  `docs/source/user_guide/templates.rst:187-192` states a template function receives `title`,
  `authors`, `date`, `body`. But `typsphinx/writer.py:260-261` merges
  `extract_toctree_options()` into the parameters unconditionally, so any master with a toctree also
  receives `toctree_maxdepth`, `toctree_numbered`, `toctree_caption`. Typst rejects undeclared named
  arguments (verified: `unexpected argument: outline_depth` on a minimal case), and neither
  `base.typ`'s `project()` (`:39-49`) nor the documented example declares an argument sink.

  Reproduced end to end: a project using the `templates.rst:144-149` example verbatim, with a
  `:maxdepth: 2` toctree, fails with
  `ExtensionError: typstpdf: 1 master document(s) failed: index: Typst compilation failed:
  TypstError: unexpected argument: toctree_maxdepth`. The in-repo example
  `docs/source/_typst/custom_template.typ:68-70` does declare all three, which is why the project's
  own docs build works. Either the documentation or the parameter passing is wrong; this also means
  adding any new template parameter is a breaking change for correctly-written custom templates.
  → Roadmapped as Phase 45.1.
