## User Constraints (from CONTEXT.md)

### Locked Decisions

**`templates_path` collision (WR-01)**

- **D-01:** A used key's resolved bundle directory that collides with Sphinx's `templates_path` is
  **refused with `ExtensionError`**, not warned about. The error names the registry key, the
  resolved bundle directory, and the colliding `templates_path` entry. This follows the shape every
  other layout-level guard in this codebase already uses -- CONF-17
  (`template_registry.py:417-424`), CONF-14 (`_validate_registry_key_references()`,
  `builder.py:780`), OUT-07 (`_validate_output_path_collisions()`, `builder.py:625`) all raise. The
  rejected alternative was `logger.warning` + skip that key's bundle copy: measured, skipping the
  copy leaves the wrapper's `#import "/_template/<key>/….typ"` pointing at a file that was never
  written, so `-b typstpdf` fails inside `typst.compile()` with an unrelated-looking error and `-b
  typst` reports success over a `.typ` tree that cannot compile. -- **Reversibility:** costly --
  every v0.8.x project that set `typst_template = "_templates/…"` alongside a `templates_path`
  containing `_templates` must move its template before it can build v0.9.0. That migration is
  announced once, in the v0.9.0 CHANGELOG, and cannot be un-announced.

- **D-02:** Detection is a **path-relationship test against the live `templates_path` config
  values** -- the bundle directory *is*, *contains*, or *is contained by* an entry -- never a name
  match on the literal string `_templates`. Measured consequences, all three of which the plans
  should assert rather than assume:
  - `examples/charged-ieee/approach2/conf.py:25` sets `typst_template = "_templates/_template.typ"`
    but sets **no** `templates_path` -> does **not** trip the check.
  - `examples/basic/conf.py:19` sets `templates_path = ["_templates"]` but no `typst_template` ->
    does **not** trip the check.
  - `examples/advanced/conf.py` sets **both** (`templates_path` at :24, `typst_template =
    "_templates/custom.typ"` at :70) -> **does** trip the check. It is the only such file in the
    tree; `docs/source/conf.py` sets `templates_path` at :45 but points `typst_template` at
    `_typst/custom_template.typ` (:96) and is unaffected.
  - `templates_path` entries are `srcdir`-relative; the comparison must resolve them against
    `srcdir` before relating them to the resolved bundle path.

- **D-03:** Multiple colliding keys are **accumulated and raised once**, in one `ExtensionError`
  naming every offending key with its colliding `templates_path` entry -- the
  `_validate_output_path_collisions()` / bundle-destination-collision idiom (`builder.py:625`,
  `builder.py:1658`), not `_validate_registry_key_references()`'s first-offender raise. Keys are
  iterated `sorted()` so the message is byte-identical across runs.

**Where the checks run (CR-01 + WR-01)**

## Summary

Both findings are narrow, well-bounded additions to an existing, well-established pattern in this
codebase: a named pre-write validation method, called once from the top of `write()`, that either
returns silently or raises one aggregated `ExtensionError`. Nothing here requires a new dependency,
a new abstraction, or a change to the build lifecycle -- it requires two things: (1) a path-
relationship predicate (bundle dir *is/contains/is-contained-by* a `templates_path` entry) built
from the same `os.path.commonpath()` idiom `_violates_conf17()` already uses one file over, and (2)
hoisting the CONF-17 check `_copy_used_template_bundles()` already runs at `finish()` time (line
1632) to also run, for the same resolved paths, inside the new pre-write pass -- while leaving the
`finish()`-side copy that runs it a second time untouched (D-06's deliberate duplication for
tests that bypass `write()`).

Both checks need a per-used-key `TemplateEngine.resolve_template()` call to get the RESOLVED bundle
path (not the declared string) -- this is the same construction `_copy_used_template_bundles()`
already performs at `builder.py:1610-1626`; the pre-write pass duplicates that construction (D-06
already accepts write()-vs-finish() duplication as the cost of covering both call paths). A
registry entry with `package` and no `template` has no bundle and is skipped by both new checks,
mirroring `_copy_used_template_bundles()`'s own skip.

The documentation half is a rename-and-replace exercise (`_templates/` -> `_typst/` in prose and in
one real fixture directory) that a repo-wide grep, re-run at discovery/execution time, shows is
larger than the floor CONTEXT.md measured: `examples/advanced/_templates/custom.typ:5` (a comment
*inside* the `.typ` file itself) is a genuine additional hit, and `examples/charged-ieee/approach2/`
carries the identical pattern (`source/_templates/_template.typ` on disk, `conf.py:25`) that
CONTEXT.md's D-08 floor names but D-09's specific rename decision does not extend to -- see Open
Questions.

**Primary recommendation:** Implement as ONE new method, `_validate_used_template_paths()` (or two
private helpers called from one caller), inserted between `_validate_registry_key_references()`
(`builder.py:961`) and `prepare_writing()` (`builder.py:964`), following
`_validate_output_path_collisions()`'s accumulate-into-`failures`-then-raise-once shape. Re-run the
repo-wide `_templates/` grep from this document (not just CONTEXT.md's floor) as the actual work
list for WR-01's documentation half, and resolve the `examples/charged-ieee/approach2/` question
before finalizing D-09's rename scope.

### Pattern 1: Accumulate-then-raise-once pre-write validator

**What:** A method that builds a `failures: List[...]` (or a `Dict[str, str]` keyed by
`_collision_key()`), appends every violation it finds while iterating a stable-ordered
(`sorted()`) input, and raises exactly one `ExtensionError` at the end naming every offender.

**When to use:** Any validation that must (a) run before any file is written and (b) report every
offending entry in one build, not just the first (D-03's explicit requirement for this phase).

**Example (the existing idiom this phase extends, read in full this session):**
```python
# Source: typsphinx/builder.py:690-778 (_validate_output_path_collisions, existing code)
claims: Dict[str, str] = {}
failures: List[Tuple[str, str]] = []

def _claim(relpath: str, description: str) -> None:
    key = self._collision_key(relpath)
    existing = claims.get(key)
    if existing is not None:
        failures.append((relpath, f"{existing} and {description} both resolve to ..."))
        return
    claims[key] = description

# ... populate claims/failures by iterating found_docs, then typst_documents ...

if failures:
    summary = "; ".join(f"{relpath!r}: {message}" for relpath, message in failures)
    raise ExtensionError(f"typst: {len(failures)} output path collision(s): {summary}")
```

### Pattern 2: Path-containment predicate via `os.path.commonpath()`

**What:** Answering "is A an ancestor of B, or B an ancestor of A, or are they the same path" with
one `commonpath()` call rather than several `startswith`/`in` checks (which are vulnerable to a
false positive like `_templatesfoo` matching a `_templates` prefix test).

**When to use:** Any "is/contains/is-contained-by" relationship between two filesystem paths where
neither path is guaranteed to exist on disk (both `templates_path` entries and a resolved template
path are pure config values, not verified to exist by this check).

**Example (the existing predicate this phase's `templates_path` check generalizes, read in full
this session):**
```python
# Source: typsphinx/template_registry.py:137-175 (_violates_conf17, existing code)
def _violates_conf17(template_abs_path: str, srcdir: str) -> bool:
    parent = os.path.normpath(os.path.dirname(os.path.abspath(template_abs_path)))
    norm_srcdir = os.path.normpath(os.path.abspath(srcdir))
    try:
        return os.path.commonpath([norm_srcdir, parent]) == parent
    except ValueError:
        # os.path.commonpath() raises ValueError on cross-drive Windows paths;
        # cross-drive paths can never share an ancestor -> False is correct.
        return False
```

**Generalizing to the three-way "is/contains/is-contained-by" test this phase needs**
(sketch -- not verbatim source, since this exact function does not exist yet):
```python
def _paths_related(path_a: str, path_b: str) -> bool:
    """True if path_a IS path_b, path_a CONTAINS path_b, or path_a IS CONTAINED BY path_b."""
    norm_a = os.path.normpath(os.path.abspath(path_a))
    norm_b = os.path.normpath(os.path.abspath(path_b))
    try:
        common = os.path.commonpath([norm_a, norm_b])
    except ValueError:
        return False  # cross-drive on Windows -- cannot be related
    return common == norm_a or common == norm_b
```
This single test covers all three of D-02's cases: `norm_a == norm_b` (both branches true),
`norm_b` under `norm_a` (`common == norm_a`), `norm_a` under `norm_b` (`common == norm_b`).

### Pattern 3: `_collision_key()` case-folded comparison

**What:** Route any two strings being compared for "same output path" through
`TypstBuilder._collision_key()` (folds `\` to `/`, `posixpath.normpath()`s, then `.casefold()`s) --
unconditionally, on every platform, no `sys.platform` branch.

**When to use:** D-07's reserved-key case check explicitly requires this (`"Typst"` vs `"typst"`).
Whether the NEW `templates_path` containment check ALSO should route its two path operands through
`_collision_key()`-style casefolding (in addition to the `commonpath()` containment test) is
flagged below in Common Pitfalls / Open Questions -- the existing `_violates_conf17()` precedent
this phase generalizes does NOT casefold (see its docstring, "pure path arithmetic ... taking no
filesystem-existence branch" -- no case discussion at all), while `_collision_key()`'s own docstring
states folding must be "unconditional on every platform" for output-COLLISION purposes. These are
two different existing precedents in the SAME codebase answering a similar-looking but distinct
question; see Open Questions.

### Anti-Patterns to Avoid

- **Naive `str.startswith()` prefix comparison:** `relpath.startswith(templates_path_entry)` matches
  `"_templatesfoo/x.typ".startswith("_templates")` -- a false positive the research brief explicitly
  names. Always split into path segments (via `commonpath()` or `Path.parts`) before comparing, never
  compare raw strings by prefix.
- **A second case-folding primitive:** D-07 explicitly forbids inventing a new casefold function for
  the reserved-key check; route through `TypstBuilder._collision_key()`.
- **Re-deriving CONF-17's predicate:** `_violates_conf17()` already exists and is imported by
  `_copy_used_template_bundles()` (`builder.py:1570`); the hoisted check must import and call the
  SAME function, never write a second copy of its `commonpath()` logic.
- **Checking the declared value instead of the resolved value:** `resolve_template_registry()`'s
  existing CONF-17 check (inside the accumulate-loop, `template_registry.py:413-425`) operates on
  `os.path.join(srcdir, template)` -- the DECLARED string, unresolved. `_copy_used_template_bundles()`'s
  A-01 check operates on `resolution.path` -- the RESOLVED path AFTER `TemplateEngine.resolve_template()`'s
  three-priority walk (explicit / search / default). CR-01's gap is specifically about the
  SYNTHESIZED `"typst"` key, whose `template` value never passes through the declared-key loop at
  all (it is assigned after that loop returns, `template_registry.py:463-468`) -- so the hoisted
  check must resolve through `TemplateEngine`, not merely re-run the declared-value check.

## Common Pitfalls

### Pitfall 1: Checking the declared `typst_template` string instead of the TemplateEngine-resolved path

**What goes wrong:** A check that runs `_paths_related(declared_string, templates_path_entry)`
without first resolving `declared_string` through `TemplateEngine.resolve_template()`'s
explicit/search/default priority walk will miss two real collision shapes: (a) the synthesized
`"typst"` key falling through to Priority 2 (the `<srcdir>/_typst/base.typ` shadow search path,
which cannot collide with `templates_path` since `_typst/` is deliberately not `_templates/`, but a
CUSTOM registry key's own search path convention could still differ) and (b) a bundle whose
resolution source is `"default"` (the packaged template, `Path(get_default_template_path())`) --
which lives INSIDE the installed Python package, never under `srcdir`, and must never be checked
against `templates_path` at all (it structurally cannot collide, and running the containment test
on it wastes work and risks a spurious result if a package happens to be installed inside the
project tree, e.g. an editable install).

**Why it happens:** The declared string and the resolved path are genuinely different values for
two of the three priorities (`"search"` and `"default"`); only `"explicit"` (a `template_path` that
was found) has the resolved path equal `Path(self.template_path)` directly, which itself may still
differ from the raw declared string if the declared string was relative and needed `srcdir`-joining
first (see `_copy_used_template_bundles()`'s own `template_path = path.join(self.srcdir,
raw_template_path)` at `builder.py:1613`).

**How to avoid:** Reuse the exact resolution construction `_copy_used_template_bundles()` already
performs (`builder.py:1610-1626`: build `template_path`, `search_paths`, `package_for_engine`,
construct `TemplateEngine`, call `.resolve_template()`, use `resolution.path`), and additionally
gate on `resolution.source != "default"` before running the `templates_path` containment test (a
default-sourced bundle's directory is the installed package's `templates/` directory, never
`srcdir`-relative, so containment against a `srcdir`-relative `templates_path` entry is always
False for it in practice -- but skipping the check for `source == "default"` avoids depending on
that always being true).

**Warning signs:** A test using the packaged default template unexpectedly trips (or unexpectedly
fails to trip) the new check; a `TemplateEngine` gets constructed with the WRONG `search_paths` list
(must be `[path.join(str(self.srcdir), TEMPLATE_SEARCH_SUBDIR)]`, matching
`_copy_used_template_bundles()` exactly, not a re-derived value).

### Pitfall 2: `templates_path` resolved against the wrong base directory

**What goes wrong:** Sphinx's own `jinja2glue.py` resolves `templates_path` entries against
`builder.confdir`, NOT `builder.srcdir`
(`cfg_templates_path = [builder.confdir / tp for tp in builder.config.templates_path]`, read from
the installed Sphinx source this session, `jinja2glue.py:186-192`). `self.confdir` defaults to
`self.srcdir` (`application.py:266-269`: `if confdir is None: self.confdir = self.srcdir`) in the
overwhelming common case (no separate `-c` conf-dir option), and every OTHER path resolution in
this codebase (CONF-17's `os.path.join(srcdir, template)`, `_copy_used_template_bundles()`'s
`path.join(self.srcdir, raw_template_path)`) already uses `self.srcdir`. D-02's own text says
"resolve them against srcdir," which is correct for the default (and overwhelmingly common) case
and consistent with every other resolution in this codebase.

**Why it happens:** `confdir` and `srcdir` are the SAME directory unless a project is invoked with
a separate configuration directory (Sphinx's `-c` command-line option) -- rare in practice, and
this codebase has no existing convention for handling that split (nothing in `typsphinx/` reads
`self.confdir` today; `srcdir` is used exclusively).

**How to avoid:** Resolve `templates_path` entries against `self.srcdir`, matching D-02 and every
existing resolution convention in this codebase. This is CORRECT for the default and near-universal
case. Document (in the new method's docstring, following this codebase's own convention of stating
known edge-case gaps explicitly, e.g. `_validate_registry_key_references()`'s own docstring) that a
project using Sphinx's separate `-c` confdir option is not covered -- exactly the same class of
narrow, named, deliberate gap this codebase already accepts elsewhere (e.g.
`_default_typst_documents()`'s single-master-only default).

**Warning signs:** A fixture project using `-c` in its test invocation behaves unexpectedly (no
such fixture exists in this test suite today, so this is unlikely to surface without deliberately
constructing one).

### Pitfall 3: `os.path.commonpath()`'s mixed-absolute/relative `ValueError`

**What goes wrong:** `os.path.commonpath()` raises `ValueError: Can't mix absolute and relative
paths` if one operand is normalized-absolute and the other is not (distinct from the cross-drive
`ValueError` `_violates_conf17()` already guards). If the new containment test resolves the bundle
path via `os.path.abspath()` but forgets to `os.path.abspath()` the `templates_path` entry (or vice
versa) before calling `commonpath()`, this raises an unhandled exception mid-build instead of a
clean `ExtensionError`.

**Why it happens:** `templates_path` entries in `conf.py` are typically written as short relative
strings (`["_templates"]`); the resolved bundle path (from `TemplateEngine.resolve_template()`) is
typically already absolute (`Path(search_dir) / self.template_name` where `search_dir` was built
from `path.join(str(self.srcdir), ...)` on an absolute `srcdir`). Both need `os.path.abspath()`
applied explicitly and unconditionally before the `commonpath()` call, matching
`_violates_conf17()`'s own `os.path.normpath(os.path.abspath(...))` on BOTH operands.

**How to avoid:** Always call `os.path.abspath()` (or `os.path.join(self.srcdir, entry)` followed by
`os.path.normpath`) on EVERY operand before `commonpath()`, never assume one side is already
absolute. Catch `ValueError` broadly (both the cross-drive and the mixed-absolute/relative shapes)
and treat it as "not related," mirroring `_violates_conf17()`'s existing `except ValueError: return
False`.

**Warning signs:** A Windows CI lane fails with an unhandled `ValueError` traceback (rather than a
clean test assertion) on a fixture with a relative `templates_path` entry -- the exact failure mode
this pitfall predicts, and the kind of Windows-only defect this project's own CLAUDE.md/memory notes
flag as a recurring class (`ci-only-defect-classes-locale-and-lint`).

### Pitfall 4: The `finish()` A-01 guard uses `raise` where the pre-write pass must `append`-then-raise

**What goes wrong:** `_copy_used_template_bundles()`'s existing A-01 check (`builder.py:1632-1639`)
raises IMMEDIATELY, per key, inside a `for key in sorted(...)` loop -- it is NOT
accumulate-then-raise-once (unlike the bundle-destination-collision check a few lines later in the
SAME method, `:1658-1663`, which IS accumulated). If the hoisted pre-write version of A-01 copies
this immediate-raise shape verbatim, it will report only the FIRST offending key, contradicting
D-03's explicit "accumulated and raised once, naming every offending key" requirement -- which
CONTEXT.md states specifically for the `templates_path` collision check, but the phase's own
internal consistency (and SC#1's "the error names the registry key" wording, singular-or-plural
unspecified) argues for treating BOTH new checks (A-01 hoist AND templates_path collision) the same
way, especially since they will likely share one iteration over the same used-key set.

**Why it happens:** Copy-pasting the existing `finish()`-side A-01 raise verbatim (which is
correct and unchanged THERE, per D-06) into the new pre-write method without adapting it to the
accumulate shape D-03 requires for the SIBLING check running in the same pass.

**How to avoid:** When both new checks (A-01 hoist, `templates_path` collision) iterate the SAME
`sorted(used_keys)` set in ONE pre-write method, accumulate failures from BOTH checks into ONE
`failures` list and raise ONE `ExtensionError` at the end -- following
`_validate_output_path_collisions()`'s pattern (which already mixes two DIFFERENT failure kinds,
destination-collision and reservation-violation, into one accumulated list). D-03 is explicit that
this applies to `templates_path` collisions; the same shape is the more internally-consistent choice
for the co-located A-01 check too (Claude's Discretion: message text/exact grouping, but the
accumulate-vs-immediate SHAPE should not silently regress from D-03's explicit requirement).

**Warning signs:** A test with TWO colliding keys only sees the first named in the error message.

### Pitfall 5: `_write_typst_files()`'s lazy fallback silently skips the new checks entirely

**What goes wrong:** Any test that calls `write_doc()` / `_write_typst_files()` directly (many
existing tests do this -- it is WHY the lazy registry fallback at `builder.py:1328-1331` exists at
all) never invokes `write()`, and therefore never runs the new pre-write pass. A new unit test
written to assert the new checks' BEHAVIOR by calling the builder's methods directly (rather than
through a real `sphinx-build` subprocess, per the established gate pattern) will silently pass even
against a broken implementation, because the code path it exercises never reaches the new checks at
all.

**Why it happens:** This is precisely D-06's stated rationale for keeping the `finish()`-side A-01
guard -- the SAME bypass applies to any new unit test that does not go through `write()` (or a full
`sphinx-build` subprocess).

**How to avoid:** Follow the established subprocess-gate pattern
(`tests/test_template_prefix_reservation_gate.py`'s `_run_sphinx_build()` helper, `sys.executable -m
sphinx` invocation) for the RED-evidence and acceptance tests -- these exercise the REAL `write()`
call chain end to end. A `temp_sphinx_app`-fixture-based unit test (like
`TestValidateRegistryKeyReferencesUnit` in `tests/test_registry_prewrite_validation_gate.py`) is
fine for testing the new method's LOGIC in isolation, but must explicitly call the new method
itself (or `builder.write(...)`), never rely on `write_doc()` reaching it.

### Pitfall 6: `tests/test_state_guard_shapes_gate.py`'s pre-existing 7-test failure

**What goes wrong:** This phase's "full suite green" gate will show 7 pre-existing failures in
`tests/test_state_guard_shapes_gate.py`, unrelated to any change this phase makes.

**Why it happens:** Documented in `.planning/phases/53-template-registry-foundation/deferred-items.md`
-- these tests read an archived `.planning/` path that predates Phase 53 and remains unfixed. STATE.md
confirms this is `[VERIFIED: .planning/STATE.md line "Run 31875380355 failed on pre-existing
test_state_guard_shapes_gate.py path defect unrelated to Phase 53, fixed by d1eff100, Run
31875707734 succeeded"]` -- a known, tracked, non-regressing failure class.

**How to avoid:** Do NOT attempt to fix these 7 failures as part of this phase's scope, and do NOT
treat their presence in a full-suite run as a sign this phase's own changes are broken. The
"full suite green" gate for THIS phase means "green except this named, pre-existing, tracked

### Sketch: repo-wide grep as an executable assertion (for the WR-01 documentation requirement)

```python
# Not verbatim source -- a sketch for the Wave 0 gap, following this codebase's existing
# glob-based structural-check convention (tests/test_preview_version_sync.py's EXAMPLES_DIR glob).
import re
from pathlib import Path

REPO_ROOT = Path(__file__).resolve().parents[1]
SEARCH_ROOTS = [REPO_ROOT / "docs" / "source", REPO_ROOT / "README.md", REPO_ROOT / "examples"]

# A LEGITIMATE templates_path = [...] Sphinx config line must not be flagged --
# only a typst_template value (or a comment/prose mentioning one) naming _templates/.
FLAGGED_PATTERN = re.compile(r"typst_template\s*=\s*['\"]_templates/")

def test_no_page_recommends_typst_template_in_templates_dir():
    hits = []
    for root in SEARCH_ROOTS:
        paths = [root] if root.is_file() else root.rglob("*")
        for path in paths:
            if path.is_file() and path.suffix in {".rst", ".md", ".py", ".typ"}:
                text = path.read_text(encoding="utf-8")
                if FLAGGED_PATTERN.search(text):
                    hits.append(str(path))
    assert not hits, f"Found _templates/-recommending typst_template in: {hits}"
```
This pattern deliberately targets `typst_template = "_templates/...` specifically (not every
occurrence of the substring `_templates`), so a legitimate `templates_path = ["_templates"]` Sphinx
config line (which SHOULD remain, per D-09) is never flagged. The exact regex/coverage scope is
Claude's Discretion, but it must be an assertion in a test file the CI suite runs, not a manual
review step -- this is what "checked by a repo-wide grep at discovery time... expressed as an
executable assertion" (research brief item 4) requires.
