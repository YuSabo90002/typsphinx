## SC#5 — /ja/stable/ handoff

because Read the Docs resolves `stable` against the tags of the repository each project builds, and
`typsphinx-doc-translations` — confirmed via `git ls-remote --heads` in this session — carries exactly


Therefore **SC#5 is discharged by a recorded handoff, not by a serving URL** — `/ja/stable/` is
explicitly **not** claimed to serve anything in this record.

**The handoff itself, in the release-set framing:** a typsphinx release tags every member of the
release set `{typsphinx, typsphinx-doc-translations}` with the same `vX.Y.Z`. In the translations
repository, the submodule pin is bumped to the parent's release commit **before** its own tag is pushed
— the tag must always name a commit whose submodule already points at the release. The consequence of
skipping a member of the set is **not** a failed build: Read the Docs resolves `stable` per-project
against that project's own tags, so a release that tags only the parent leaves the ja project with no
matching tag and `/ja/stable/` simply **404s** — invisible to CI, not a red build anyone would notice.

This exact wording is recorded in the translations repository's own `README.md` § "Release procedure —
a two-repository release set", re-fetched directly in this session to confirm it is actually there, not
merely planned:

### Viewer caveat

The owner reports `pdf_viewer=zen-twilight` on `os=nixos`. Zen Browser is a Firefox-derived (Gecko-based)
browser; absent a separately configured external PDF handler, its default in-browser PDF viewing is
Firefox's built-in `pdf.js` viewer, which does its own glyph rendering and font substitution independent

anything, be more likely to paint *something* recognizable in place of a missing glyph than to leave a
visible blank/tofu box — so a `tofu` result surviving through such a viewer's own substitution machinery
is comparatively strong evidence *for* the glyph's absence, not weak evidence undermined by a
permissive viewer. The reverse is not true with the same strength: an `ok` result from a substitution-
capable viewer would have been comparatively weaker evidence of correct rendering, since the same
substitution machinery could paint over a genuinely absent glyph with a look-alike from a fallback font.

observed here.

also render visibly wrong; or (b) the glyph paints correctly from some embedded font subset whose
`ToUnicode` CMap is broken or missing for that specific codepoint, which would render visibly fine despite
the broken text layer.

**A broken `ToUnicode` CMap (explanation (b)) corrupts text *extraction* only — it cannot, by itself,
produce a visually blank or tofu-substituted glyph on the rendered page.** The CMap is consulted only
when software copies or searches the text layer; the glyph outline the PDF viewer paints comes from the
font's glyph table, addressed directly by glyph ID, not through the `ToUnicode` mapping. A page can
therefore have a completely broken `ToUnicode` entry and still paint a perfectly correct-looking
ideograph — that is precisely explanation (b)'s premise.

result.

### 1. The patch — full diff of the staged file

```diff

+++ b/.planning/phases/30.1-translations-repository-japanese-rtd-site/translations-repo/.github/workflows/update-pin.yml
@@ -44,11 +44,31 @@ jobs:
       - name: Set up Python
         run: uv python install 3.12
 
+      - name: Fetch the tracked branch into the submodule
+        # actions/checkout@v7's `submodules: true` runs `git submodule update --init --force
+        # --depth=1`, which fetches the submodule by its pinned commit SHA (a --depth=1,
+        # commit-scoped fetch) rather than by branch name, so it never creates a
+        # `refs/remotes/origin/<branch>` remote-tracking ref inside the submodule's own .git.
+        # The next step, `git submodule update --remote`, needs exactly that ref to resolve "the
+        # tip of the tracked branch"; without it the step exits 128 with `fatal: Unable to find
+        # refs/remotes/origin/<branch> revision in submodule path 'typsphinx'` -- exactly what run
+        # 30188423465 hit. This step creates that ref explicitly. The branch name is read from
+        # .gitmodules at runtime, not hard-coded, so the owed post-merge flip of that field to
+        # `main` cannot silently re-break this workflow.
+        run: |
+          branch=$(git config -f .gitmodules submodule.typsphinx.branch)
+          echo "Tracked branch: $branch"
+          git -C typsphinx fetch --depth=1 origin "refs/heads/$branch:refs/remotes/origin/$branch"
+          git -C typsphinx rev-parse --verify "refs/remotes/origin/$branch"
+          echo "Submodule HEAD before update: $(git -C typsphinx rev-parse HEAD)"
+
       - name: Advance submodule to latest tracked branch
         # The branch this follows comes from .gitmodules' `branch` field, not from whatever was
         # checked out when the submodule was added. This is a different knob from RTD's own
         # Admin "Default branch" setting -- the two are independent, on two different systems.
-        run: git submodule update --remote typsphinx
+        run: |
+          git submodule update --remote typsphinx
+          echo "Submodule HEAD after update: $(git -C typsphinx rev-parse HEAD)"
 
       - name: Create virtual environment
         run: uv venv
```
