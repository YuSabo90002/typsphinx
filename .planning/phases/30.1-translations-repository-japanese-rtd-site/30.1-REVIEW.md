## Summary

This is the gap-closure round of Phase 30.1 (plans 07-11). This report **replaces** the prior
wave-1-5 `30.1-REVIEW.md` in full (that file reviewed a different, smaller file set:
`tests/test_readthedocs_config.py` and `docs/source/contributing.rst`).

**Prior finding WR-01 (broken clone command in `contributing.rst`) is CONFIRMED FIXED** in this
round — re-read `docs/source/contributing.rst:301-310` directly rather than inheriting the old
verdict. The clone command now reads `git clone --recurse-submodules
https://github.com/YuSabo90002/typsphinx-doc-translations.git` followed by `cd
typsphinx-doc-translations`; both name the same repository and `--recurse-submodules` is present,
so the submodule is populated before `make locale-update` runs. The referenced `make locale-update`
/ `make locale-stat` targets also exist verbatim in the staged
`.planning/.../translations-repo/Makefile`. This finding is not carried forward.

No Critical/blocker-level defects were found in this round's five files. Specifically verified,
not merely assumed:
- `derive_typst_lang` exists in `typsphinx/template_engine.py`, is `None`-safe, and its docstring
  confirms returning `None` (rather than raising or hardcoding `"en"`) is deliberate so the
  template's own default applies.
- `conf.py`'s manual replication of the derivation is technically necessary, not redundant: cross-
  checked `TemplateEngine.uses_bundled_default_template()` in `typsphinx/template_engine.py`, which

  so `writer.py`'s own auto-derivation path (`typsphinx/writer.py:230-233`) never fires here, and
  without `conf.py`'s explicit call the Japanese PDF would silently render with the template's
  `lang: "en"` default regardless of the actual doc language.
- `custom_template.typ` is byte-identical to the bundled `templates/base.typ` except for the one
  documented `font:` line; its four `@preview` import lines currently match
  `writer.py`/`template_engine.py`/`templates/base.typ` exactly (checked with `grep`).

  parse cleanly under `yaml.safe_load`.
- `black --check` and `ruff check` pass clean on `docs/source/conf.py`.
- `tests/test_readthedocs_config.py` and `tests/test_preview_version_sync.py` both pass (7/7),
  confirming (per the findings below) that neither actually asserts anything about this round's
  new files.

The three issues below are quality/coverage gaps, not incorrect current behavior: a documentation

## Warnings

### WR-01: `contributing.rst` Translations workflow omits the dependency-install step

**File:** `docs/source/contributing.rst:301-310`
**Issue:** The new "Translations" section instructs a contributor to `git clone
--recurse-submodules .../typsphinx-doc-translations.git`, `cd` into it, then immediately run `make
locale-update`. Per the staged `.planning/.../translations-repo/Makefile`, `make locale-update`
invokes `sphinx-build -M gettext ...` and `sphinx-intl update ...` directly. Neither binary is
installed by the clone, and this repository's own `contributing.rst` "Development Setup" section
(the only install instructions given anywhere in this file) covers setting up *this* repo
(`typsphinx`), not the freshly cloned `typsphinx-doc-translations` checkout — a different root
with its own `pyproject.toml`-less top level. A reader following the instructions verbatim in a
clean environment hits `sphinx-build: command not found` (or a missing-`typsphinx`/missing-
`sphinx-intl` import failure if some unrelated `sphinx-build` happens to already be on `PATH`)
before ever reaching `make locale-stat`. The parallel `README.md` staged for the same repository
has the identical gap (noted for context only — not in this review's file list).
**Fix:** Add an explicit install step between the `cd` and the first `make` invocation, e.g.:
```rst
   # Clone the translations repository
   git clone --recurse-submodules https://github.com/YuSabo90002/typsphinx-doc-translations.git
   cd typsphinx-doc-translations

   # Install the submodule's package with its docs extras (provides sphinx-build, sphinx-intl)
   uv venv && uv pip install --python .venv/bin/python ./typsphinx[docs]
   source .venv/bin/activate

   # Refresh the catalogs against the current English source
   make locale-update
```
or, at minimum, state plainly that `sphinx-build`/`sphinx-intl` (from `typsphinx[docs]`) must
already be importable in the active environment before `make locale-update` will succeed.

### WR-02: `custom_template.typ` is an unguarded fourth `@preview` version-lockstep site

**File:** `docs/source/_typst/custom_template.typ:39-44`
**Issue:** CLAUDE.md documents a known hazard: the four Typst Universe `@preview` package versions
(`codly`, `codly-languages`, `mitex`, `gentle-clues`) must stay in lockstep across three files
(`typsphinx/writer.py`, `typsphinx/template_engine.py`, `typsphinx/templates/base.typ`), guarded by
`tests/test_preview_version_sync.py` so a future single-file version bump fails CI loudly instead
of silently. `custom_template.typ` (new this round) copies all four import lines verbatim from
`base.typ` — but reading `test_preview_version_sync.py` directly confirms its
`WRITER_PATH`/`TEMPLATE_ENGINE_PATH`/`BASE_TYP_PATH` constants and its `EXAMPLES_DIR.rglob("*.typ")`
scan (`EXAMPLES_DIR = REPO_ROOT / "examples"`) never reach `docs/source/_typst/`. The versions
happen to match today (verified all four lines are identical to `base.typ`), but a future version
bump applied to the canonical three sites (or to the `examples/` tree, which this test does watch)
would silently leave `custom_template.typ` stale with zero CI signal — precisely the failure mode
this test suite exists to prevent, now reintroduced through an untested fourth copy that renders
both the English and Japanese production PDFs.
**Fix:** Either (a) add `docs/source/_typst/custom_template.typ` as a fourth path constant in
`tests/test_preview_version_sync.py::test_preview_versions_identical_across_declaration_sites` (or
extend its glob to also cover `docs/source/_typst/`), or (b) generate this file's import block
programmatically from the canonical version constants instead of hand-copying it, making drift
structurally impossible rather than merely untested.

### WR-03: Staged `translations-repo` deliverables have no structural test coverage

**File:** `.planning/phases/30.1-translations-repository-japanese-rtd-site/translations-repo/.readthedocs.yaml` (whole file), `.planning/phases/30.1-translations-repository-japanese-rtd-site/translations-repo/.github/workflows/update-pin.yml` (whole file)
**Issue:** The parent repository's own `.readthedocs.yaml` is guarded by `test_readthedocs_yaml_shape`
and `test_readthedocs_yaml_pdf_override` in `tests/test_readthedocs_config.py`, which assert its PDF
job's shape (temp build dir, `mkdir -p "$READTHEDOCS_OUTPUT/pdf/"` ordering before the `cp`,
`formats: [pdf]` paired with `build.jobs.build.pdf`, etc.). The staged ja manifest reviewed here is
a hand-maintained mirror of that exact structure — its own comment states "Same four commands as
the parent's build.jobs.build.pdf ... so this job satisfies the same structural bar
tests/test_readthedocs_config.py enforces on the parent's PDF job" — but grepping the full `tests/`
tree for `translations-repo`, `post_create_environment`, `submodules`, and every `python.install`
key confirms zero matches: no test anywhere references this staged file or `update-pin.yml`'s shell
logic (branch resolution from `.gitmodules`, the `pin_moved`/`po_changed` decision gate, etc.). A
future edit to the parent's `.readthedocs.yaml` PDF job (e.g. a changed temp-directory path,
reordered `mkdir`/`cp` steps, or a renamed `docs/source`) has no CI signal forcing this mirrored
manifest to update in lockstep — the same "must stay in sync or ship silently wrong" hazard class
already guarded for the `@preview` versions (WR-02), recurring here without a guard. Per this
round's scope these are still `.planning`-staged artifacts rather than the live repository, so this
is correctly not Critical — but it is a real gap to close once these files are promoted.
**Fix:** When these files are promoted into the live `typsphinx-doc-translations` repository, add
a structural test there (mirroring `test_readthedocs_yaml_shape`) asserting the PDF job shape, the
`submodules: {include: all}` requirement, and the `post_create_environment` locale-copy ordering
(`rm -rf` before `cp -a`); and add a shell-logic test (or at minimum a `shellcheck`/`actionlint` CI
step) for `update-pin.yml`.
