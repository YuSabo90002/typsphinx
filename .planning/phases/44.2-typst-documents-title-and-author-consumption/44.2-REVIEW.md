# Phase 44.2: Code Review Report

**Reviewed:** 2026-08-06T20:01:07Z
**Depth:** standard
**Files Reviewed:** 15
**Status:** issues_found

## Summary

This is round 3 of the `typst_authors` precedence-prose correction. The core mechanism —
`_resolve_entry_element()` in `writer.py` and the target-key-based seed/overwrite logic in
`TemplateEngine.map_parameters()` — is sound and is now backed by an unusually rigorous test
suite: `tests/test_params_authors_writers.py` derives its expected-value predicate from an
independent transcription of the rule and cross-checks it against an AST enumeration of every
`params[...]` write site in `map_parameters()`, and `tests/test_entry_metadata_route_uniformity.py`
exercises all four template routes end-to-end. Every test file reviewed here passes (142/142,
verified this session) and traces correctly against the code as written.

Two problems were found, both by tracing published claims against reachable configurations rather
than by re-deriving the rule from scratch (per the phase's own stated failure mode):

1. A **freshly introduced** sentence in the just-corrected `configuration.rst` Precedence
   paragraph ("and nothing else in typsphinx replaces it") is false — it is contradicted by a
   sentence three paragraphs later in the *same* document, and I reproduced the falsifying
   configuration end-to-end (built `.typ` output attached below) to confirm the contradiction is
   real and not just a wording nitpick. This is exactly the defect class this phase exists to
   close, shipped a third time in the very prose written to fix rounds 1 and 2.
2. `writer.py`'s `effective_elements` merge (unconditional, every master document) crashes with an
   unhandled `TypeError` — not a graceful `ExtensionError` — when `typst_elements` is set to a
   non-`dict` truthy value. This predates phase 44.2 (introduced in phase 27.1's CONF-07 work) but
   lives in a file this phase's review scope explicitly includes, and I reproduced it with a real
   `sphinx-build` run.

## Critical Issues

### CR-01: Precedence paragraph's "nothing else in typsphinx replaces it" is false — falsified by the very next override rule stated in the same document

**File:** `docs/source/user_guide/configuration.rst:189-229` (specifically line 194)

**Issue:**

The Precedence paragraph, rewritten in this phase's round-3 correction (commit `784c9f9`), reads:

> typsphinx seeds `authors` from `typst_authors` first and then applies the mapping, so whatever
> the mapping writes into `authors` replaces that seed -- **and nothing else in typsphinx replaces
> it.**

This is presented as a general claim about the `authors` value's whole lifecycle in typsphinx, not
scoped to `map_parameters()` alone. It is false: three paragraphs later, in the *very same* Author
Information section (line 227-228, unchanged by this round's edit — it was already there before
`784c9f9` and survived it untouched), the document itself states the counterexample:

> `typst_template_function`'s dict-form `params` take precedence over both.

"Both" refers to the entry's author element and `typst_authors` — i.e. `typst_template_function`'s
`params["authors"]` **is** something else in typsphinx that replaces whatever `map_parameters()`
decided, at `render()` time. The two sentences describe the same code path and contradict each
other within the same document section.

**Falsifying configuration** (built and verified this session — `sphinx-build -b typst` on this
exact `conf.py` reproduces the contradiction in the emitted `.typ` file):

```python
project = "P"
author = "A"
release = "1.0"

typst_documents = [("index", "index", "T", "Entry Author")]

typst_authors = {"Jane Doe": {"organization": "MIT"}}
typst_template_mapping = {"project": "title"}  # omits "author" -> "authors":
                                                # per the Precedence paragraph's own rule,
                                                # this is exactly the case where the
                                                # typst_authors seed "survives ... and
                                                # nothing else in typsphinx replaces it"
typst_template_function = {
    "name": "project",
    "params": {"authors": ("Explicit Override Author",)},
}
```

Measured output (`index.typ`):

```
  authors: ("Explicit Override Author",),
```

Not `Jane Doe` / `MIT` (the `typst_authors` seed the paragraph claims survives unreplaced), and not
`Entry Author` (the entry's own author value) either — `typst_template_function`'s `params["authors"]`
won, exactly as the *rest* of the document (correctly) says it should. The isolated "nothing else...
replaces it" sentence is what's wrong, not the code and not the rest of the prose.

This matters specifically because this document's own drift guard,
`tests/test_params_authors_writers.py::test_configuration_rst_documents_both_target_key_shapes`,
only checks for the *presence* of certain phrases — it does not (and structurally cannot, being a
substring check) detect that one of those phrases is self-contradicting another passage in the same
file. Nothing in the test suite would have caught this on its own.

**Fix:** Scope the claim to `map_parameters()`'s own seed/mapping race, and cross-reference the
`render()`-level override explicitly at the point the claim is made, e.g.:

```rst
typsphinx seeds ``authors`` from ``typst_authors`` first and then applies the mapping, so whatever
the mapping writes into ``authors`` replaces that seed -- and nothing else *inside
map_parameters()* replaces it. (``typst_template_function``'s dict-form ``params``, applied later
in ``render()``, can still replace whatever ``map_parameters()`` produced -- see below.)
```

or simply delete the clause and let the pre-existing "take precedence over both" sentence (already
correct) carry that half of the story without a nearby claim that contradicts it.

## Warnings

### WR-01: `effective_elements` merge crashes with an unhandled `TypeError` on a non-`dict` `typst_elements`

**File:** `typsphinx/writer.py:319-321`

**Issue:**

```python
effective_elements = ({"lang": auto_lang} if auto_lang else {}) | (
    typst_elements or {}
)
```

`typst_elements` is registered via `add_config_value("typst_elements", {}, "html", [dict])`
(`typsphinx/__init__.py:48`), and Sphinx's type-checking for `add_config_value` only **warns** on a
type mismatch — the mistyped value is still passed through unchanged, not coerced or rejected. If a
user sets `typst_elements` to any non-`dict` *truthy* value (a list, a string, a tuple — a plausible
conf.py typo, e.g. copying the `typst_template_assets` list-of-strings pattern by mistake), the
`or {}` guard does not fire (the value is truthy), and `dict | list` (or `dict | str`) raises
`TypeError: unsupported operand type(s) for |`.

Reproduced this session with `sphinx-build -b typst` and `typst_elements = ['not', 'a', 'dict']`:
Sphinx logs its own type-mismatch warning, continues the build, then crashes with an unhandled
Python traceback out of `TypstWriter.translate()` (build `returncode=2`, full traceback dumped to
the user, no `ExtensionError` with an actionable message) — this aborts the entire build on the
first master document, not just that document.

This predates phase 44.2 (the merge itself was introduced in phase 27.1's CONF-07 work,
`cf22574`/`4a41c27`), but it lives in `writer.py`, a file explicitly in this phase's review scope,
runs unconditionally for every master document phase 44.2's own `_resolve_entry_element()` machinery
sits next to, and is a genuine unhandled crash on a plausible misconfiguration rather than a
descriptive `ExtensionError` matching this codebase's existing convention (e.g.
`map_parameters()`'s own `ExtensionError` for an unknown `typst_elements` key).

**Fix:** Normalize on type, not truthiness, before the merge:

```python
if typst_elements is not None and not isinstance(typst_elements, dict):
    logger.warning(
        f"typsphinx: typst_elements must be a dict, got {type(typst_elements).__name__} "
        f"-- ignoring it for this document."
    )
    typst_elements = {}

effective_elements = ({"lang": auto_lang} if auto_lang else {}) | (typst_elements or {})
```
