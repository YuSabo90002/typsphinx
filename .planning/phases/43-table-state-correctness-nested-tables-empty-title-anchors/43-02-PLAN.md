<objective>
Get the milestone branch `gsd/v0.7.1-bug-fix-round` onto `origin` and a CI run started against it,
during Phase 43 — roadmap SC#5 and milestone invariant #5.

Purpose: v0.7.0 shipped after eight phases during which the milestone branch was never pushed, so
neither the Windows CI lanes nor a real tag push ever ran against it until the release PR. Both
defects that surfaced at the v0.7.0 close share that single cause. Pushing in wave 1 of the first
phase of the milestone gives the platform lanes the maximum possible runway.

Output: `43-GATE-EVIDENCE-02.md` recording the `git ls-remote` hit, the triggered workflow run, and
the complete lane list.

**Why this plan carries all four requirement IDs:** it ships no code for any of them. SC#5 is a
phase-level roadmap criterion, not a requirement-level one — but the CI surface it opens is the
surface every one of TBL-04, TBL-05, FIG-01 and QUA-01's changes must pass through before the
milestone ships, and plan 43-05 confirms a completed run against the tip that carries all four.
</objective>

**D-P1 — When the branch is pushed: wave 1 of Phase 43, and again in the final wave.** Measured this
planning session: `git ls-remote --heads origin` lists `main`, two `dependabot/*` branches,
`gsd/v0.7.0-api-rendering-design-overhaul` and two `worktree-agent-*` branches — the v0.7.1 milestone

#5 is to surface platform breakage early. Recording a known-red Windows lane and proceeding to Phase
44 anyway would reproduce exactly the v0.7.0 failure it was written to prevent, one phase later.
Enforcement lives in plan 43-05 (a `<verify><human-check>` on the completed run), not here — this
plan only starts the clock. Stated here so it is recorded once, in the plan that owns SC#5's push.
</planner_decisions>
