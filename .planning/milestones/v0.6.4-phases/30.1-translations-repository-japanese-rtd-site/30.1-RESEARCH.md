## Summary

The translations repository is not a generic "second Sphinx project" — it is a thin shell whose only
jobs are (1) hold a git submodule pinned to a `typsphinx` commit, (2) hold the relocated `.po`
catalogs at its own top level, (3) copy those catalogs into the submodule's expected
`locale_dirs = ["../locale/"]` location before Sphinx runs, and (4) install the submodule's own
`pyproject.toml` (dependencies + `docs` extra) so `sphinx-build` has everything it needs. Every piece
of this mirrors `sphinx-doc/sphinx-doc-translations`'s measured shape one-for-one, adapted only for
the fact that typsphinx is a Sphinx **extension** (needs `sys.path` + `pip install`) rather than
Sphinx itself (needs only `pip install -e .`), and for typsphinx's specific `locale_dirs` path shape
(`../locale/` relative to `conf.py`, not Sphinx's own `locale_dirs = ["locales"]`).

The single most consequential finding this session adds beyond what Phase 30's discussion already
measured: **RTD's own `ubuntu-24.04` build image ships `fonts-noto-cjk-extra` and `fonts-hanazono`
pre-installed at the Docker-image level**, independent of any project's `build.apt_packages`
[VERIFIED: readthedocs-docker-images `Dockerfile`, `github.com/readthedocs/readthedocs-docker-images`].
This directly explains Phase 29's "fonts-noto-cjk is already the newest version" apt log line and the
`HanaMinA` (Hanazono Mincho) font Typst actually embedded — `fonts-hanazono` was on the image before
the parent's manifest ever declared `build.apt_packages: [fonts-noto-cjk]`. The practical consequence
for this phase: the apt line very likely is **not** load-bearing for CJK glyph correctness on RTD, but
keeping it costs nothing (one YAML line, zero risk) and should be carried into the ja manifest
unchanged rather than removed — removing it to test the hypothesis is a separate, non-blocking
experiment, not something this phase needs to resolve to ship.

The second load-bearing finding: `conf.py`'s `gettext_auto_build = True` (already set, read-only,
unchanged) means Sphinx compiles `.po` → `.mo` automatically at build time. The translations
repository therefore never needs to commit `.mo` binaries or run a separate compile step — only
`.po` source files need to be relocated and kept current, which simplifies both the manifest and the
D-08 pin-bump workflow's diff surface.

**Primary recommendation:** Build `typsphinx-doc-translations` with submodule directory `typsphinx/`,
top-level catalog directory `locale/` (singular, matching this repository's own `docs/locale/`
naming), a `post_create_environment` step that `cp -a`s `locale/` into `typsphinx/docs/locale/`
(exactly where `locale_dirs = ["../locale/"]` already looks, zero `conf.py` edits), a
`python.install` entry of `{method: pip, path: typsphinx, extra_requirements: [docs]}` (non-editable
is fine — the checkout is immutable per build), and a `formats: [pdf]` + `build.jobs.build.pdf`
override structurally identical to the parent's (D-01), with paths adjusted for the submodule prefix.

This is docs-hosting/CI/metadata work, not a client-server application — the standard tier vocabulary
is adapted below to the two repositories and RTD's own infrastructure involved.

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Japanese HTML/PDF rendering | RTD Build (CI-like, ephemeral container) | — | RTD's own build sandbox runs `sphinx-build`/`typst.compile()` per commit; no server-side runtime persists between builds |
| Translated string storage | Source/Repo (translations repo, `locale/`) | — | `.po` catalogs are plain-text source, version-controlled, not a database |
| Submodule pin currency | CI/Automation (GitHub Actions, D-08) | Source/Repo (commit that records the pin) | The pin is a git object (a commit SHA reference) but only *advances* via an automated job — without it the pin is inert |
| Served HTML/PDF delivery | CDN/Static (RTD's own hosting + flyout) | — | Once built, RTD serves static HTML/PDF artifacts; no origin server logic per-request |
| RTD project linking (parent ↔ translation) | Owner-manual (RTD web UI) | — | No `.readthedocs.yaml` or API surface exists for this; it is dashboard-only, unassertable by any test |
| `.pot`/`.po` regeneration | CI/Automation (D-08 workflow) | Source/Repo (human-runnable entry point, D-12 discretion) | Automated for freshness; a human entry point exists for manual translation work between automated runs |

### Pattern 1: Zero-`conf.py`-edit catalog placement via `post_create_environment`

**What:** Instead of overriding `locale_dirs` (which would require editing the submodule's `conf.py`
— forbidden, both by milestone invariant #3's spirit and because the submodule is a read-only mirror
of this repository), copy the translations repo's top-level `locale/` directory into the exact
filesystem location the submodule's *existing, unedited* `conf.py` already expects.

**When to use:** Any time a submodule's `conf.py` cannot be edited but its build-time inputs
(translation catalogs) must be supplied from outside the submodule.

**Example:**
```yaml
# .readthedocs.yaml (translations repo)
# Source: sphinx-doc-translations's own measured `post_create_environment: cp -a locales sphinx/doc/`,
# adapted for typsphinx's `locale_dirs = ["../locale/"]` (relative to docs/source/conf.py, i.e.
# docs/locale/ from the submodule root) rather than Sphinx's own `locale_dirs = ["locales"]`.
build:
  jobs:
    post_create_environment:
      - mkdir -p typsphinx/docs/locale
      - cp -a locale/. typsphinx/docs/locale/
```
This runs before `python.install` in RTD's build lifecycle (`post_checkout` → `pre_create_environment`
→ `create_environment` → `post_create_environment` → `pre_install` → `install` → `post_install` →
`pre_build` → `build` → `post_build` [CITED: docs.readthedocs.com/platform/stable/build-customization.html]),
so the catalogs are in place well before Sphinx ever runs.

### Pattern 2: Installing a submodule extension via `python.install: path:`

**What:** RTD's `python.install` supports a list entry `{method: pip, path: <relative-dir>,
extra_requirements: [<extra>]}` — `pip install <path>` with extras, path relative to the repository
root [CITED: docs.readthedocs.com/platform/stable/config-file/v2.html — documented example:
`python.install: [{method: pip, path: ., extra_requirements: [docs]}, {method: pip, path:
another/package}]`].

**When to use:** When the package under documentation lives in a subdirectory (here, a submodule)
rather than the repository root — exactly typsphinx-doc-translations's shape.

**Example:**
```yaml
python:
  install:
    - method: pip
      path: typsphinx
      extra_requirements:
        - docs
```
This is deliberately **not** editable (`-e`) — the Sphinx-doc-translations precedent uses `pip install
-e sphinx …` via a custom `build.jobs.install` override (bypassing `python.install` entirely, since
`method: pip` has no documented editable flag), but editability only matters when the installed
package is expected to be modified after install. The submodule checkout is immutable for the
lifetime of a single RTD build container, so a plain (non-editable) `path:` install behaves
identically and needs no `build.jobs.install` override — simpler, and it is the officially documented
mechanism rather than a custom job reimplementing what `python.install` already does.

### Pattern 3: `.pot`/`.po` regeneration entry point (D-12 arrival half)

**What:** A human-runnable command sequence, callable both by a developer and by the D-08 automated
workflow, that regenerates `.pot` from the submodule's current English source and merges it into the
`locale/` catalogs.

**Example:**
```bash
# Source: this repo's own docs/Makefile gettext/locale-update targets (Phase 29 D-06 precedent),
# adapted for the translations repo's directory layout.
sphinx-build -M gettext typsphinx/docs/source typsphinx/docs/_build
sphinx-intl update -p typsphinx/docs/_build/gettext -d locale -l ja
```
`sphinx-intl update`'s `-d`/`--locale-dir` flag overrides whatever `locale_dirs` `conf.py` declares
[CITED: `uv run sphinx-intl update --help`, this worktree], so the command works correctly even though
it is invoked from the translations repo root, not from inside the submodule. This is the D-12
arrival-half's human-runnable entry point; Claude's Discretion item — a thin Makefile target
(`locale-update: sphinx-build -M gettext … && sphinx-intl update …`) mirroring this repo's own
`docs/Makefile` naming convention is the recommended shape so translators moving between the two
repositories find a familiar command.

### Anti-Patterns to Avoid

- **Editing the submodule's `conf.py` to point `locale_dirs` at the translations repo's top-level
  `locale/`:** the submodule is a read-only mirror of this repository's tree at a pinned commit —
  "editing" it would mean either committing a divergent conf.py into `typsphinx-doc-translations`
  itself (defeating the whole "same source" premise of a submodule) or editing this repository's own
  `conf.py`, forbidden per this phase's explicit read-only instruction. The `post_create_environment`
  copy step (Pattern 1) achieves the same effect with zero edits anywhere.
- **Committing regenerated `.mo` binaries in the D-08 workflow:** wasted diff noise given
  `gettext_auto_build = True` already handles compilation at Sphinx build time (see Alternatives
  Considered above).
- **Diffing raw `git diff` output to decide "commit if changed":** every `sphinx-intl update` run
  rewrites each `.po` file's `POT-Creation-Date` header line even when zero `msgid`/`msgstr` content
  changed [VERIFIED: `docs/locale/ja/LC_MESSAGES/index.po`'s existing header includes
  `"POT-Creation-Date: 2025-11-01 21:21+0900\n"`, read directly from this repository]. A naive
  "any diff → commit" rule produces a no-op commit every single scheduled run. See Common Pitfalls
  below for the concrete mitigation.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| `.pot` → `.po` merging | A custom msgid-diffing script | `sphinx-intl update` (already in `pyproject.toml`'s `docs` extra) | It already handles line-wrap width, obsolete-message pruning (`--no-obsolete`), and multi-language batching; a hand-rolled merge would re-derive gettext's own merge semantics incorrectly. |
| PDF glyph/page/text comparison | A committed comparison script | The same hand-run `pypdf` commands Phase 29's D-12 gate already used, pasted verbatim into the verification record | Explicitly forbidden by D-03/D-15 precedent — the RTD-built PDF is unreachable from CI, so a committed script would look like a gate that never runs. This is not a "don't hand-roll" in the reuse sense but a "don't automate what cannot actually run automatically" discipline this milestone has already established twice (Phase 29 D-15, this phase's D-03). |
| Submodule pin tracking | A cron job that re-clones the parent repo wholesale and diffs commits | `git submodule update --remote` (standard git plumbing) | Git already tracks the pinned commit as a first-class object; re-implementing "what's the latest commit on the tracked branch" is exactly what `--remote` does. |

**Key insight:** every piece of custom automation this phase would otherwise be tempted to write
(catalog diffing, PDF comparison, submodule tracking) already has a standard tool that does it
correctly — the actual engineering work is *wiring* those tools together across two repositories and
one RTD build sandbox, not inventing new logic.

## Common Pitfalls

### Pitfall 1: "commit if changed" churns daily on `POT-Creation-Date` alone

**What goes wrong:** The D-08 workflow runs `sphinx-build -M gettext` + `sphinx-intl update` on a
schedule. `sphinx-intl update` calls `msgmerge` internally, which rewrites every `.po` file's
`POT-Creation-Date` header to match the freshly generated `.pot`'s timestamp — **every run**, even
when not a single `msgid`/`msgstr` pair changed. A naive `git diff --quiet || commit` rule therefore
produces a content-free commit on every scheduled run, defeating the entire point of "commit if
changed."

**Why it happens:** gettext's own toolchain treats `POT-Creation-Date` as always-current metadata, not
as translatable content — it is a side effect of *regenerating* the `.pot`, independent of whether the
English source text actually changed.

**How to avoid:** Count only non-header diff lines before deciding to commit:
```bash
CHANGED=$(git diff -- locale | grep -E '^[+-]' | grep -v -E '^[+-]{3}' \
  | grep -v '"POT-Creation-Date' | wc -l)
if [ "$CHANGED" -gt 0 ]; then
  git add typsphinx locale && git commit -m "..." && git push
else
  echo "no substantive change; discarding regenerated headers"
  git checkout -- locale
fi
```
This is a general-purpose gettext-CI pattern [ASSUMED — standard technique, not sourced from an
authoritative doc; grounded in the directly-verified fact that `POT-Creation-Date` exists and changes
on every `sphinx-intl update` run]. The planner should treat the exact filter expression as an
implementation detail to be tested, not a locked API.

**Warning signs:** A daily commit history in `typsphinx-doc-translations` with identical-looking
diffs and no actual translation change; SC#3's "demonstrated by an observed run that moves the pin"
criterion would then be trivially always-true and therefore useless as a signal.

### Pitfall 2: `git submodule update --remote` needs an explicit tracked branch

**What goes wrong:** Without `submodule.typsphinx.branch` set in `.gitmodules`, `--remote` falls back
to whatever branch the submodule's own `HEAD` pointed to at the time it was first added — which may
not be `main` if the submodule was added while `HEAD` was a milestone branch (this repository's own
Phase 29 evidence shows RTD's Default Branch was temporarily pointed at
`gsd/v0.6.4-read-the-docs-migration` during this exact milestone).

**Why it happens:** Git's submodule tracking branch is a `.gitmodules` field (`branch = <name>`), not
inferred fresh on every `--remote` call — it is set once when the submodule is added and stays fixed
until edited.

**How to avoid:** Explicitly set `branch = main` in `.gitmodules` when creating the submodule,
regardless of what branch happens to be checked out in the parent repository at that moment. Do not
conflate this with RTD's own "Default branch" **Admin** setting (a different, RTD-dashboard-only
concept governing which branch RTD's `latest` version tracks) — they are two independent knobs on two
different systems.

### Pitfall 3: `fonts-noto-cjk` may be redundant, but do not remove it to "clean up"

**What goes wrong:** Phase 29's build log shows `fonts-noto-cjk is already the newest version` — i.e.
it was present on the RTD image *before* `apt_packages` ran, and RTD's own `readthedocs-docker-images`
Dockerfile confirms `fonts-noto-cjk-extra` and `fonts-hanazono` are baked into the base image
[VERIFIED: `github.com/readthedocs/readthedocs-docker-images/blob/main/Dockerfile`, referencing
`readthedocs/readthedocs.org#6319`]. It would be tempting to drop the apt line from the ja manifest as
dead weight.

**Why it happens:** The evidence that the line is *currently* redundant does not prove it will *stay*
redundant — RTD's base image is out of this project's control and could change; the apt line is a
one-line, zero-risk insurance policy against that.

**How to avoid:** Carry `build.apt_packages: [fonts-noto-cjk]` into the ja manifest unchanged (same
value as the parent's, per symmetry). If the planner wants to empirically settle whether it is
load-bearing, that is a separate, explicitly-scoped experiment (remove the line, rebuild, diff the
embedded font list) — not a prerequisite for shipping this phase, and not something this phase's
success criteria require.

### Pitfall 4: RTD project creation does not imply linking, and linking does not imply version activation

**What goes wrong (restated from the Phase 30 discussion, load-bearing enough to repeat here):**
creating the ja RTD project against `typsphinx-doc-translations` and creating the English project
against this repository are two fully independent actions. Without the explicit **Settings →
Translations** link on the *parent* project, RTD's flyout will not offer the en↔ja switch on either
site even though both build successfully. Without **independent version activation** on the ja
project, no version (not even `latest`) may be servable there at all — translation projects inherit
nothing from the parent.

**How to avoid:** Treat "project created" as a separate, verifiable-only-by-owner checkbox from
"project linked" and "versions activated" — three distinct owner-manual steps, not one.

**Warning signs:** `/ja/latest/` 404s even though the ja project's own build log shows success; or
`/ja/latest/` serves content but the flyout on `/en/latest/` shows no language switcher at all.

### D-08 pin-bump GitHub Actions workflow (translations repository)

```yaml
# Source: skeleton modelled on sphinx-doc-translations's main.yml with Transifex coupling removed,
# per D-08's explicit instruction. contents: write on the default GITHUB_TOKEN is sufficient to push
# back to the SAME repository -- no PAT/cross-repo secret needed [CITED: docs.github.com/en/actions/
# writing-workflows/choosing-what-your-workflow-does/controlling-permissions-for-github_token].
name: Update translation source pin

on:
  schedule:
    - cron: "0 6 * * *"
  workflow_dispatch: {}

permissions:
  contents: write

jobs:
  update-pin:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          submodules: true

      - name: Advance submodule to latest parent main
        run: git submodule update --remote typsphinx

      - uses: actions/setup-python@v6
        with:
          python-version: "3.12"

      - name: Install typsphinx (submodule) with docs extras
        run: pip install -e ./typsphinx[docs]

      - name: Regenerate .pot from current English source
        run: sphinx-build -M gettext typsphinx/docs/source typsphinx/docs/_build

      - name: Update .po catalogs from fresh .pot
        run: sphinx-intl update -p typsphinx/docs/_build/gettext -d locale -l ja

      - name: Detect substantive change (ignore POT-Creation-Date-only churn)
        id: diff
        run: |
          CHANGED=$(git diff -- locale | grep -E '^[+-]' | grep -v -E '^[+-]{3}' \
            | grep -v '"POT-Creation-Date' | wc -l)
          echo "changed=$CHANGED" >> "$GITHUB_OUTPUT"

      - name: Commit and push if changed
        if: steps.diff.outputs.changed != '0'
        run: |
          git config user.name "github-actions[bot]"
          git config user.email "github-actions[bot]@users.noreply.github.com"
          git add typsphinx locale
          git commit -m "chore: advance typsphinx submodule pin + resync ja catalogs"
          git push
```

**No `repository_dispatch` trigger from the parent repository** (Claude's Discretion, resolved):
adding one would require a new workflow step or secret in *this* repository — `.github/workflows/`
edits here are out of this phase's file-touch list and would create unwanted coupling between two
milestone phases' commits. `schedule` + `workflow_dispatch` is self-contained inside
`typsphinx-doc-translations` alone and still satisfies SC#3's "demonstrated by an observed run" via
the manual `workflow_dispatch` trigger.

## Open Questions

1. **Does RTD's default clone depth affect resolving the pinned submodule commit?**
   - What we know: RTD's own docs mention a `submodules` config key for cloning submodules but do not
     document clone-depth interaction with submodule pin resolution [attempted fetch of
     `docs.readthedocs.com/platform/stable/reference/git-integration.html` found no explicit
     statement]. Standard git behavior is that `git submodule update` fetches the specific pinned
     commit directly regardless of the superproject's own clone depth.
   - What's unclear: whether RTD's specific clone/checkout implementation deviates from vanilla git
     in a way that would break this.
   - Recommendation: not a phase-blocking unknown — if it breaks, the first real RTD build for the ja
     project fails loudly and visibly in the raw build log, exactly the same evidentiary path Phase 29
     used for the `@preview` egress unknown. Do not pre-solve; observe the first build log.

2. **Is `build.apt_packages: [fonts-noto-cjk]` actually load-bearing for CJK glyph correctness on
   RTD?**
   - What we know: RTD's base `ubuntu-24.04` Docker image already ships `fonts-noto-cjk-extra` and
     `fonts-hanazono` [VERIFIED, `readthedocs-docker-images` Dockerfile]; Phase 29's apt log literally
     said "already the newest version," and the embedded font was `HanaMinA` (from `fonts-hanazono`,
     also pre-installed), not a Noto-named font.
   - What's unclear: whether removing the apt line changes anything at all (untested — no build has
     ever run without it).
   - Recommendation: keep the line (zero cost, symmetry with parent, Pitfall 3). Treat "does removing
     it change the embedded font list" as an optional, non-blocking follow-up experiment outside this
     phase's success criteria — this phase's D-03 gate only requires CJK *coverage*, which is already
     evidenced regardless of which package provides it.
