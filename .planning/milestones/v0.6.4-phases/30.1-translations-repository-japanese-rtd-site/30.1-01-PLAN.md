verifiable rather than exploratory.

Three items left open to planning are settled here. Every later plan in this phase depends on them.

**PD-01 — `docs/locale/ja/`'s removal from this repository belongs to Phase 30, not Phase 30.1.**
(CONTEXT.md § Claude's Discretion, last bullet.) Reasons, in order of weight:
1. `worktree.cleanup-wave`'s deletion guard blocks any branch containing deletions with **no bypass**
   (PROJECT.md D-13, Phase 27 precedent, restated in STATE.md § Blockers). Phase 30 is already
   deletion-heavy and already expects one manual merge. Putting this deletion there costs **one**
   manual-merge event for the milestone instead of two.
2. D-15's ordering constraint says Phase 30's deletions wait on 30.1's replacement being confirmed
   working. Placing the catalog deletion in Phase 30 *is* that ordering, expressed as a commit boundary
   rather than as a convention someone has to remember.
3. SC#4's glyph gate builds a local `SPHINX_LANGUAGE=ja` PDF **from this repository**. That build reads
   `docs/locale/ja/` through the unedited `locale_dirs = ["../locale/"]` seam. Deleting the catalogs
   inside this phase would remove the baseline the phase's own hardest criterion depends on.

Consequence to carry into Phase 30: this repository's `docs/locale/ja/` and the translations
repository's `locale/` **will diverge** between Plan 05 (which adds new English msgids under
`docs/source/contributing.rst` and lets the pin-bump workflow merge them into the translations-side
catalogs only) and Phase 30's deletion commit. That divergence is deliberate and time-boxed; the
translations side is authoritative from Plan 03 onward. It must be stated in the evidence record, not
silently tolerated, and no task in this phase may "fix" it by regenerating this repository's catalogs.

**PD-02 — the submodule tracks `gsd/v0.6.4-read-the-docs-migration`, not `main`.**
RESEARCH.md Pitfall 2 recommends `branch = main`. That recommendation is **wrong for this milestone's
actual state**, measured 2026-07-26 in this checkout:

- `git ls-tree --name-only origin/main -- .readthedocs.yaml` → **empty**. `origin/main` carries no RTD
  build manifest at all.
- `git show origin/main:docs/source/conf.py | grep -c _resolve_language` → **0**. `origin/main`'s
  `conf.py` cannot read `READTHEDOCS_LANGUAGE`.

A submodule tracking `main` would therefore pin a tree that RTD refuses to build, and whose `conf.py` —
if it built at all — would resolve `language` to `"en"` regardless of the ja project's Admin Language
setting. That is I18N-01's named failure mode, delivered by construction. The submodule tracks the
milestone branch for the duration of v0.6.4. This mirrors the parent RTD project, whose own Default
branch is already pointed at the same milestone branch (Phase 29; the flip back to `main` is already a
recorded post-merge handoff in STATE.md § Deferred Items).

Consequence: the post-merge handoff list grows from two items to **three** — (a) parent RTD project
Default branch → `main`, (b) ja RTD project Default branch → `main`, (c) the translations repository's
`.gitmodules` `branch` field → `main` followed by one pin-bump run. Plan 04 records all three.

**PD-03 — the phase's live-evidence record is named `30.1-EVIDENCE.md`, not `30.1-VERIFICATION.md`.**
`{phase}-VERIFICATION.md` is a name `/gsd-verify-work` owns and rewrites. Phase 29 wrote its

<assumption_delta_decision>
The `assumption-delta` checkpoint fired with two signals. Both are resolved here for the whole phase.

**Signal 1 — `chosen` / `configurable`: `no-change`.** False positive, confirmed. The snippet
("configurable: RTD derives the URL segment from the project's Language using ISO 639-1, and `jp` is…")
is D-10, which states the URL segment is **not** configurable and that there is nothing to decide. This
is the opposite of a constant becoming a parameter; no representation changed.

**Signal 2 — `pluralization` / `second`: `promote`.**

- **Noun that is now primary:** *the release set* — the set of repositories a typsphinx release tags.
  Not "the release", and not "the project".
- **Decision: `promote`.** The release procedure is written to name a release set
  `{typsphinx, typsphinx-doc-translations}` whose members are tagged `vX.Y.Z` in lockstep, with the
  translations repository's submodule bump ordered before its tag. It is **not** written as "tag this
  repository, then also tag the translations repository".
- **Rationale (one line):** D-07 makes two-repository tagging permanent and structural (REL-02 requires
  `/ja/stable/`, and RTD resolves `stable` against the tags of whichever repository a project builds),
  so an appended second step is exactly the shape a future release silently skips — and the symptom is
  a 404 on `/ja/stable/`, not a failed build.
- **Where it is written down:** two durable places, both in this phase. (1) The translations
  repository's `README.md` § "Release procedure — a two-repository release set" (Task 3 of this plan),
  because that is the repository whose maintainer needs it. (2) `30.1-EVIDENCE.md` § "Handoffs" (Plan
  04 Task 3), which Phase 33 reads. This phase does **not** edit `/gsd-complete-milestone`'s own skill
  definition — that is framework configuration outside this milestone's scope; Phase 33 owns carrying
  the release set into the publish procedure, and the handoff record is what hands it over.
- **Suggested invariant check (offered, not planned as a task):** before publishing, compare
  `git ls-remote --tags <parent>` and `git ls-remote --tags <translations>` for the release tag; a tag
  present in one and absent from the other goes red. This belongs to Phase 33 or to
  `/gsd-complete-milestone`, not here.
