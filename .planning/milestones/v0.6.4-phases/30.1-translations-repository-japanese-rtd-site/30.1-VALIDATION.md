# Phase 30.1 — Validation Strategy

> Per-phase validation contract for feedback sampling during execution.
> Seeded by plan-phase from `30.1-RESEARCH.md` § Validation Architecture.

**Standing caveat for this phase:** most of the verification surface is deliberately
**not** hermetic-pytest-shaped. It is owner-manual RTD web-UI action, one-off live HTTP
fetches, and a hand-run PDF comparison — the exact shape D-03 + Phase 29's D-15 require
("no comparison script is committed", because the RTD-built PDF is unreachable from CI and
a committed script would look like a gate that never runs). Do not read the thin automated
column as thin verification; read the Manual-Only table as the phase's real gate.

## Test Infrastructure

| Property | Value |
|----------|-------|
| **Framework** | pytest 8.x (existing, `tests/` in this repository) |
| **Config file** | `pyproject.toml` `[tool.pytest.ini_options]` (existing, unchanged) |
| **Quick run command** | `uv run pytest tests/test_readthedocs_config.py -q` |
| **Full suite command** | `uv run pytest -q` |
| **Estimated runtime** | ~2s quick / ~3–5 min full suite |

**Worktree note (CLAUDE.md § Worktree-isolated execution):** provision with
`env -u VIRTUAL_ENV -u UV_PROJECT_ENVIRONMENT uv sync --extra dev` first, then run
everything through `uv run`. Without it the executor edits the worktree but pytest imports
the unchanged main-tree package.

---

## Sampling Rate

- **After every task commit:** `uv run pytest tests/test_readthedocs_config.py -q` — the only
  hermetic surface this phase touches — plus, where applicable, a fresh live fetch against
  whatever RTD state exists at that point.
- **After every plan wave:** `uv run pytest -q` (full suite) — confirms no collateral breakage
  in the existing baseline.
- **Before `/gsd-verify-work`:** full suite green, **plus a fresh re-fetch** of `/ja/latest/`
  and a fresh ja PDF comparison. Mirror `29-VERIFICATION.md`'s "independently re-checked live"
  discipline — do not trust a mid-execution snapshot.
- **Max feedback latency:** ~2s for the quick command; the live/manual checks are inherently
  latency-unbounded and are gate-time, not per-task, evidence.

## Manual-Only Verifications

| Behavior | Requirement | Why Manual | Test Instructions |
|----------|-------------|------------|-------------------|
| `/ja/latest/` serves actual translated strings from a full-coverage docname | I18N-01 (SC#1) | The live RTD site is unreachable from CI, and a committed fetch test would be a gate that never runs. Milestone invariant #7: a green build proves nothing about content. | `curl -sS -L https://typsphinx.readthedocs.io/ja/latest/user_guide/builders/` and grep for a **specific `msgstr` value** taken from `user_guide/builders.po` (65/65 coverage). Do **not** probe `changelog`, `contributing`, `api/index`, or `user_guide/templates` — all 0% translated; they render all-English on a perfectly healthy site. Paste command + matched line verbatim into the evidence record. |
| RTD flyout offers en↔ja **from both sites**; ja project's versions independently activated | I18N-01 (SC#2) | RTD web-UI state. No test in this repository can assert it. Linking under the parent's Settings → Translations is the step most likely to be missed — two working but unswitchable sites otherwise. | Owner observes the flyout on both `/en/latest/` and `/ja/latest/`. Optionally corroborate with `https://readthedocs.org/api/v3/projects/<parent-slug>/translations/` showing the ja project. Record both. |
| Submodule pin advances automatically; `/ja/latest/` reflects a post-creation source change | I18N-01 (SC#3) | Requires an **observed** GitHub Actions run plus RTD rebuild latency — not reproducible in a test process. | Record the workflow run URL, the commit it pushed (pin before → after), and a fetched `/ja/latest/` body showing the new source content. A run that only rewrote `POT-Creation-Date` does **not** count as a demonstrated pin move. |
| ja PDF is glyph-correct, not merely built | I18N-03 (SC#4) | The RTD-built PDF is unreachable from CI. D-03 + Phase 29 D-15 forbid committing a comparison script. | Build the **same commit** locally with `SPHINX_LANGUAGE=ja sphinx-build -b typstpdf docs/source <tmp>`. Machine-check with `pypdf` (already in the `dev` extra): page-count equality, extracted-text equality, and at least one embedded `/BaseFont` with CJK coverage. Baseline measured 2026-07-26: **94 pages / 1,811,337 bytes / 9 fonts / 1,997 CJK chars in the first 30 pages**. Replicate `29-VERIFICATION.md` § "D-12 Baseline"'s invocation shape. Paste commands and output verbatim. |
| Sampled ja pages render Japanese, not tofu | I18N-03 (SC#4, human half) | Visual judgment. No machine substitute — font embedding is necessary but not sufficient for correct rendering. | Owner opens the RTD-built PDF, samples a handful of pages (planner's discretion which), and confirms Japanese glyphs. If the owner does not confirm, the honest-verifier rule applies: abstain to `human_needed`, never assert an unevidenced truth. |
| `/ja/stable/` handoff recorded | I18N-01 (SC#5) | `stable` cannot exist before the `v0.6.4` tag. The criterion is discharged by a **recorded handoff**, not by a serving URL. | Confirm the ja project's Default Version is `latest`, and that the two-repository tag step (submodule bump → tag push in `typsphinx-doc-translations`) is written into the release procedure. Same shape as Phase 29's `latest` → `stable` handoff. |
