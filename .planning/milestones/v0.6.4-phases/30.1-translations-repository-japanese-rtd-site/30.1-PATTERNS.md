## Pattern Assignments

### `typsphinx-doc-translations/.readthedocs.yaml` (config, batch)

**Analog:** `.readthedocs.yaml` (this repository, full file — 58 lines, already read in full above)

This is the single most load-bearing analog in the phase: the ja manifest must be a **deliberate
variant** of the parent's, not an independent design. Every section below cites the parent's exact
current text so the new file's diff-from-parent is legible.

**`build.os` / `build.tools` / `build.apt_packages`** (parent lines 6-18):
```yaml
build:
  os: ubuntu-24.04
  tools:
    python: "3.12"
  apt_packages:
    - fonts-noto-cjk
```
Carry `fonts-noto-cjk` into the ja manifest **unchanged** — RESEARCH.md's Pitfall 3 explicitly
forbids removing it "to clean up" even though it is empirically likely redundant (RTD's base image
already ships `fonts-noto-cjk-extra`/`fonts-hanazono`). Symmetry with the parent, zero cost.

**`build.jobs.build.pdf`** (parent lines 19-34) — the shape the ja PDF job must mirror, with paths
adjusted for the submodule prefix (`typsphinx/docs/source` instead of `docs/source`):
```yaml
  jobs:
    build:
      pdf:
        - mkdir -p /tmp/typst-pdf-build/doctrees
        - sphinx-build -b typstpdf -d /tmp/typst-pdf-build/doctrees docs/source /tmp/typst-pdf-build/out
        - mkdir -p "$READTHEDOCS_OUTPUT/pdf/"
        - cp /tmp/typst-pdf-build/out/*.pdf "$READTHEDOCS_OUTPUT/pdf/"
```
Note the two hard constraints this pattern encodes (both asserted by
`tests/test_readthedocs_config.py`, see below): exactly one `sphinx-build` invocation, and the
`mkdir` for `$READTHEDOCS_OUTPUT/pdf/` must precede the `cp`. The ja manifest additionally needs a
`post_create_environment` step (RESEARCH.md Pattern 1) that runs *before* this — see RESEARCH.md's
own worked example, not reproduced here since it is new content, not copied from this repo.

**`sphinx.configuration`** (parent line 36-37):
```yaml
sphinx:
  configuration: docs/source/conf.py
```
Ja variant: `typsphinx/docs/source/conf.py` (submodule prefix). This is the file RESEARCH.md
confirms stays **read-only** — the ja manifest supplies catalogs via `post_create_environment`
copying into the location this *unedited* `conf.py`'s `locale_dirs = ["../locale/"]` already
resolves against (conf.py line 58, captured below).

**`formats:` + the comment explaining why both must appear together** (parent lines 39-45):
```yaml
formats:
  - pdf
```
Parent's own comment is the exact rationale to replicate in the ja manifest: omitting
`build.jobs.build.pdf` while declaring `formats: [pdf]` would silently activate RTD's default
LaTeX pipeline instead of typsphinx's own `typstpdf` output.

**`python.install`** (parent lines 47-57):
```yaml
python:
  install:
    - method: uv
      command: sync
      extras:
        - docs
```
This is the parent's own installer, **not** what the ja manifest should copy verbatim — RESEARCH.md's
Pattern 2 (already researched, not re-derived here) specifies `{method: pip, path: typsphinx,
extra_requirements: [docs]}` instead, because the ja manifest's package lives in a submodule
subdirectory, not the repository root. Flagged here so the executor does not reflexively copy the
parent's `uv sync` form.

### `typsphinx-doc-translations/.github/workflows/update-pin.yml` (config, event-driven — D-08)

**Analogs (three, composited):** `.github/workflows/drift.yml` (scheduled-job skeleton),
`.github/workflows/docs.yml` (build/publish step conventions), `.github/workflows/ci.yml`
(Python/uv setup conventions).

**Trigger + permissions shape** (from `drift.yml` lines 1-11):
```yaml
on:
  schedule:
    - cron: '0 0 * * 1'
  workflow_dispatch:

permissions:
  contents: read
  issues: write
```
Copy the `schedule` + `workflow_dispatch` dual-trigger shape. The ja workflow's own permissions
must be narrowed to `contents: write` only (it pushes a commit, does not open issues) — this is a
deliberate deviation from `drift.yml`, not a copy error; RESEARCH.md's Security Domain section
already flags `contents: write` scoping as the phase's one genuine security-relevant surface.

**Checkout + uv/Python setup convention** (from `ci.yml` lines 26-34, repeated verbatim across
every job in that file):
```yaml
steps:
  - uses: actions/checkout@v7

  - name: Install uv
    uses: astral-sh/setup-uv@v7
    with:
      version: "latest"

  - name: Set up Python
    run: uv python install 3.12
```
This is this repository's standing convention for "get a Python + uv toolchain into a GitHub
Actions runner" — replicate it exactly (same action versions, same step names) rather than
inventing a different setup shape. Note `docs.yml` (line 19-27) uses a slightly different two-step
form (`actions/setup-python@v6` then `astral-sh/setup-uv@v7` separately) — `ci.yml`'s single
`astral-sh/setup-uv@v7` + `uv python install` form is the more common convention (4 of 5 jobs in
`ci.yml` use it) and is the one to prefer.

**Failure-reporting idiom** (from `drift.yml` lines 37-52) — reference only, likely not needed for
D-08 since D-08's failure mode is "silently doesn't run," not "loudly fails a build" — but worth
knowing this repository's established idiom for turning a failed scheduled job into a deduplicated
GitHub issue exists, in case the planner wants parity:
```yaml
- name: Report drift via a single deduplicated issue
  if: failure()
  env:
    GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
    GH_REPO: ${{ github.repository }}
  run: |
    existing=$(gh issue list --label drift --state open --json number --jq '.[0].number')
    ...
```

**Build/artifact step naming convention** (from `docs.yml` lines 21-38) — the "one `name:` per
logical step, imperative mood" convention to match:
```yaml
- name: Setup Python
  uses: actions/setup-python@v6
  with:
    python-version: "3.12"
...
- name: Install dependencies
  run: |
    uv sync --extra dev --extra docs --locked
    uv pip install -e .
```

RESEARCH.md's own Code Examples section already has a fully composed `update-pin.yml` built from
these three analogs plus D-08's specific command sequence (`git submodule update --remote` →
`sphinx-build -M gettext` → `sphinx-intl update` → filtered diff → conditional commit/push) — treat
that as the target shape; the excerpts above are the *conventions* it must match against this
repo's existing workflows, not a duplicate of content already fully specified in RESEARCH.md.

### `typsphinx-doc-translations/` locale-tooling entry point (utility, batch — D-12 arrival half)

**Analog:** `docs/Makefile` (this repository), lines 15-28 in full:
```makefile
.PHONY: help Makefile gettext locale-init locale-update html-ja multilang serve-multilang

# Internationalization (i18n) targets
gettext:
	@$(SPHINXBUILD) -M gettext "$(SOURCEDIR)" "$(BUILDDIR)" $(SPHINXOPTS) $(O)
	@echo "Build finished. The message catalogs are in $(BUILDDIR)/gettext."

locale-init:
	sphinx-intl update -p $(BUILDDIR)/gettext -l ja
	@echo "Locale initialized. Translation files are in locale/ja/LC_MESSAGES/."

locale-update:
	sphinx-intl update -p $(BUILDDIR)/gettext -l ja
	@echo "Locale updated. Translation files are in locale/ja/LC_MESSAGES/."
```
Two things to note when adapting this into the translations repository:
1. `SOURCEDIR = source` (Makefile line 8) is relative to `docs/` in *this* repo (i.e.
   `docs/source`). In the translations repo, the equivalent path is `typsphinx/docs/source`
   (submodule prefix) — the target-directory arguments must shift, the verb sequence
   (`gettext` build then `sphinx-intl update`) must not.
2. `locale-init` and `locale-update` here are **identical bodies** — this repository never
   actually differentiated first-run vs. update. The translations-side entry point (Makefile
   target, script, or documented command, per Claude's Discretion) can collapse this into a single
   target without losing any behavior that exists today.

`sphinx-intl update -p <gettext-dir> -l ja` is the exact command; RESEARCH.md's Pattern 3 confirms
`sphinx-intl update` accepts a `-d`/`--locale-dir` override (not used by this repo's own Makefile,
because here `locale_dirs` in `conf.py` already points at the right place) — the translations-side
entry point will need `-d locale` (or wherever the top-level catalog directory lands) since it is
invoked from the translations-repo root, not from inside `docs/`.

### `typsphinx-doc-translations/locale/ja/LC_MESSAGES/*.po` (data, file-I/O — relocated catalogs)

**Analog:** `docs/locale/ja/LC_MESSAGES/*.po` (this repository) — the exact files being moved, not
rewritten. Current layout, confirmed by directory listing (13 `.po` + 13 `.mo`, 2026-07-26):
```
docs/locale/ja/LC_MESSAGES/
├── api/index.po
├── changelog.po
├── contributing.po
├── examples/advanced.po
├── examples/basic.po
├── examples/index.po
├── index.po
├── installation.po
├── quickstart.po
├── user_guide/builders.po
├── user_guide/configuration.po
├── user_guide/index.po
└── user_guide/templates.po
```
Only the `.po` files need to move — `gettext_auto_build = True` (see `conf.py` excerpt below)
means `.mo` binaries are compiled at build time and should **not** be committed into the
translations repository (RESEARCH.md's Anti-Patterns section makes this explicit; committing `.mo`
would just add binary-diff noise to every D-08 pin-bump commit).

**The exact `conf.py` seam these catalogs must land in front of** (this repository,
`docs/source/conf.py` lines 47-61, **read-only for this phase**):
```python
def _resolve_language():
    return os.getenv("READTHEDOCS_LANGUAGE", os.getenv("SPHINX_LANGUAGE", "en"))


# READTHEDOCS_LANGUAGE (RTD's Language setting) wins over SPHINX_LANGUAGE (local/CI override); defaults to "en".
language = _resolve_language()

locale_dirs = ["../locale/"]  # Path is relative to the conf.py file
gettext_compact = False  # Generate separate .pot files for each document
gettext_uuid = False  # Do not use UUIDs in .pot files
gettext_auto_build = True  # Automatically build gettext catalogs
```
`locale_dirs = ["../locale/"]` is relative to `conf.py`'s own location (`docs/source/conf.py`), so
it resolves to `docs/locale/` — meaning in the submodule (mounted at `typsphinx/` in the
translations repo), the same relative path resolves to `typsphinx/docs/locale/`. This is exactly
why RESEARCH.md's Pattern 1 copies the top-level `locale/` directory into
`typsphinx/docs/locale/` via `post_create_environment` rather than editing this file: the
*unedited* seam already looks there. `gettext_compact = False` is why the catalog layout is
per-docname (`api/index.po`, not one giant `messages.po`) — the relocated tree must preserve this
exact per-file structure, not flatten it.

### RTD manifest structure (config-file-v2 top-level key ordering and comment density)
**Source:** `.readthedocs.yaml` (this repository, full file)
**Apply to:** the ja `.readthedocs.yaml` — match the parent's key order (`build` → `sphinx` →
`formats` → `python`) and its convention of a one-to-three-line comment above every
non-obvious line explaining *why*, not just *what*. The parent file is dense with rationale
comments specifically because this milestone's own precedent (Phase 29) treats the manifest as
executable documentation for future editors; the ja manifest should read the same way.

### sphinx-intl invocation shape
**Source:** `docs/Makefile` lines 18-28
**Apply to:** both the D-12 locale-tooling entry point and the D-08 workflow's catalog-regeneration
step — `sphinx-build -M gettext <source> <builddir>` followed by
`sphinx-intl update -p <builddir>/gettext -l ja` (add `-d <locale-dir>` when not invoked from
inside `docs/`).
