## User Constraints (from CONTEXT.md)

### Locked Decisions

Typst の組版言語 (`set text(lang:)`) を Sphinx の `language` conf に連動させる。`templates/base.typ` の `project()` に `lang` パラメータを追加し、**既定テンプレートを実際に使う経路のみ** `config.language` から自動導出し、`typst_elements["lang"]` の明示指定が全経路で優先する。

**実測で確定した前提（discuss 中に実測 — 前提として使ってよい、再調査不要）**

| `set text(...)` | figure / table supplement |
|---|---|
| `lang: "en"` | Figure 1 / Table 1 |
| `lang: "ja"` | 図 1 / 表 1 |
| `lang: "de"` | Abbildung 1 / Tabelle 1 |
| `lang: "fr"` | Fig. 1. – / Tableau 1. – |
| `lang: "zh"` (region 無し) | 图 1 / 表 1 |
| `lang: "zh", region: "TW"` | **圖** 1 / 表 1（region で変わる唯一の実測ケース） |
| `lang: "pt"` (region 無し) | Figura 1 / Tabela 1 |

- ロケール付き値 (`"zh_CN"`, `"日本語"`, `""`) の素通しは Typst 側で **hard fatal**（`expected two or three letter language code`）。
- 未知の2〜3文字コード（`"xyz"`）は fatal にならず英語にフォールバックする。大文字 (`"JA"`) も成功する。
- supplement の区切りは ASCII 空白ではなく **NBSP (`\xa0`)**。
- CJK 抽出はフォント環境依存（`ignore_system_fonts=True` で豆腐 `\x00`）。
- `<srcdir>/base.typ` は同梱テンプレートを **黙って上書き** する（`load_template()` Priority 2）。

**D-01: region は非対応 — `lang` のみ。** `base.typ` の変更は `project()` への `lang` パラメータ追加とその `set text()` 配線の1パラメータのみに限る（SC#5）。結果 `zh_TW` は簡体字「图 1」になる — 既知の限界として docs に明記し受容する。

**D-02: 変換は汎用規則、マップ表は持たない。** 「先頭から最初の区切り文字（`_`/`-`/`@`）までを取り小文字化」の1行規則。`ja`→`ja`、`zh_CN`→`zh`、`pt-BR`→`pt`、`sr@latin`→`sr`、`en`→`en`。

**D-03: 変換後が2〜3文字英字にならなければ `lang` を渡さず `logger.warning` で値を名指しする。** `params`に`lang`を入れないので `base.typ` の既定値 (`"en"`) が効く。明示的に `"en"` を渡す案・`ExtensionError` で fail loud する案はどちらも却下（後者は `language` が typsphinx 自身の設定ではなく Sphinx 標準設定であるため）。

**D-04: 明示 `typst_elements["lang"]` は検証せず素通し。** Phase 26 D-09 の先例に一致。D-03 の検証は自動導出値にのみ適用する。

**D-05（precedence）: `lang` を `ELEMENTS_ALLOWLIST` に `STRING` 種別で追加し、優先順位は既存構造に任せる。** elements マージが `map_parameters` の最後に走るので、自動導出値を先に `params["lang"]`（相当）に入れておけば明示指定が後から上書きする。**新しい precedence 分岐ロジックを書かないこと。**

**D-06（判定境界）: 「既定テンプレート経路」は宣言ではなく *ロード結果* で判定する。** `typst_template is None and typst_package is None` という宣言ベースの判定は `<srcdir>/base.typ` シャドウ経路を見逃す。判定は「実際にロードされるテンプレートが同梱の `base.typ` か」に一致させる（`load_template`/`get_template_content` の解決結果を利用 — どの経路で解決したかを返す小さな手入れが必要）。判定は writer 側の `TemplateEngine`（params を作る側）で行う。`builder.py::_write_template_file` は `_template.typ` を書くだけで params を作らないので、そちらに判定を重複させない（WR-04）。

**D-07: GATE-01 の証明方式。** `ja` は「実コンパイル成功 + `.typ` に `lang: "ja"`」で証明し、supplement の言語連動は `de` の PDF テキスト抽出（`"Abbildung 1"`/`"Tabelle 1"`）で証明する分割方式。CI の ubuntu ランナーの CJK フォント有無が未確認なため。ROADMAP SC#1 の文面はこの分割証明で読むこと — verifier はこれを未達と扱わない。

**D-08: SC#3 の非破壊回帰フィクスチャは2ケース。** ① `typst_template` に `lang` 未宣言のカスタムテンプレートを明示指定 + `language = "ja"` → ビルド成功。② `<srcdir>/base.typ` に `lang` 未宣言のテンプレートを置く（`typst_template`/`typst_package` は未設定）+ `language = "ja"` → ビルド成功（D-06 の判定境界そのものの証明）。

**D-09: docs もこのフェーズで更新する。** `docs/source/user_guide/configuration.rst`（`typst_elements` 対応キー記述に `lang` を追加、既定テンプレート以外では自動導出されないこと、`zh_TW` が簡体字になる限界を明記）+ `docs/locale/ja/LC_MESSAGES/user_guide/configuration.po` の追従（Phase 27 と同じスコープ限定 `sphinx-build -b gettext`、`#~` は手で剥がさない）。

## Summary

This phase is structurally identical in shape to Phase 26 (CONF-04): a Python-side config-plumbing
addition riding the `ELEMENTS_ALLOWLIST`/`map_parameters(typst_elements=)` mechanism Phase 26 built,
plus (unlike Phase 26) one new `base.typ` parameter — permitted this phase only by the 2026-07-25
milestone-invariant amendment. Every fact CONTEXT.md needed to *decide* the behavior (lang→supplement
mapping, locale-suffix fatal, NBSP separator, `<srcdir>/base.typ` shadowing) was already measured
during `/gsd-discuss-phase` with real `typst.compile()` and is treated here as a fixed premise, not
re-verified. This research instead reads the actual code the plan must change, to convert five
locked *decisions* into a concrete, low-blast-radius *implementation shape* — the area CONTEXT.md
explicitly deferred to research/planning.

The single most important finding, not previously surfaced: **`writer.py`'s per-document `render()`
path does not call `load_template()`/`get_template_content()` at all for the normal (non-package)
master-document case.** Only `builder.py::_write_template_file()` (which runs once per build, writes
the shared `_template.typ`, and never builds `params`) actually resolves and reads the template file
via `TemplateEngine.get_template_content()` → `load_template()`. `writer.py::translate()` skips
`self.load_template()` entirely because `render()` almost always takes the `if template_file:` branch
(importing the separately-written `_template.typ`), not the `else: self.load_template()` branch (that
branch only fires in the package-alone case, where `load_template()` is also skipped because
`self.typst_package` short-circuits it). D-06 requires the default-template-path judgment to happen
in writer.py (params-building side, not builder.py), but writer.py currently has no reason to ever
call `load_template()` — this phase must add that call (on writer.py's own, separately-constructed
`TemplateEngine` instance, which is built with identical `template_path`/`search_paths` inputs to
builder.py's instance, so the two independently-computed resolutions agree by construction — the same
pattern `resolve_package_for_engine()` already establishes for the package/template routing decision,
WR-04). The `map_parameters()` merge-order chain (`parameter_mapping` → package-path back-fill guard →
`typst_authors` override → elements merge, elements merge LAST) was read directly and confirmed
unchanged since Phase 26 — D-05's "no new precedence branching" requirement is satisfiable with ZERO
code changes inside `map_parameters()` beyond the one-line `ELEMENTS_ALLOWLIST["lang"] = STRING`
addition, provided the auto-derived value is pre-merged into the SAME `typst_elements` dict in
`writer.py` *before* it reaches `map_parameters()` (ordinary Python dict union, explicit value applied
last so it wins on collision) — this is the recommended shape (see Pattern 3).

**Primary recommendation:** (1) Add `lang: "en"` to `base.typ`'s `project()` signature and wire it to
`set text(size: fontsize, lang: lang)` — the only `base.typ` edit permitted (SC#5). (2) Add
`"lang": _ElementsEmissionKind.STRING` to `ELEMENTS_ALLOWLIST` in `template_engine.py`, in the SAME
commit as (1). (3) Give `TemplateEngine.load_template()` a companion resolution step that records
*which* priority (`explicit` / `search` / `default`) resolved as a side-effect attribute (or small
dataclass), without changing `load_template()`'s or `get_template_content()`'s existing `-> str`
signatures (zero blast radius on the ~5 existing `tests/test_template_engine.py` call sites or
`builder.py:585`). (4) In `writer.py::translate()`, after constructing the master-document
`TemplateEngine` (already-existing code, unchanged args), call the new resolution step; if it resolved
`"default"`, derive `lang` from `config.language` via the D-02 split-at-first-separator rule, validate
it against D-03's 2–3-letter-alpha rule (warn-and-omit via `logger.warning` on failure — the existing
idiom already used twice in this codebase), and pre-merge `{"lang": derived} | (typst_elements or {})`
into the dict passed to `map_parameters(typst_elements=...)` — never touching `map_parameters()`
itself beyond the allowlist entry. (5) Two GATE-01 real-compile fixtures mirroring
`tests/test_typst_elements_pass_through_gate.py`'s existing skeleton, plus two non-regression
fixtures (D-08) mirroring the existing `tests/test_template_engine.py` search-priority tests.

### Supporting
Not applicable — no new supporting/helper libraries. The `lang`-code conversion is a one-line string
transform (`value.split("_")[0].split("-")[0].split("@")[0].lower()` or equivalent, per D-02) requiring
no library; validation is a `len(x) in (2, 3) and x.isalpha()` check, also stdlib-only.

### Alternatives Considered
| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| A hand-maintained, generic `_`/`-`/`@`-split conversion rule (D-02, locked) | A full BCP-47/Babel-backed language-tag parser (e.g. `langcodes` package) | **Rejected per CONTEXT.md D-02** (already decided) — would be a new runtime dependency (violates the milestone invariant) for a problem the one-line split rule already solves for every case CONTEXT.md measured; `langcodes` is also unnecessary because the ONLY output space that matters is "2-3 letter alpha or nothing", not full locale semantics |
| Pre-merging the auto-derived `lang` into the `typst_elements` dict in `writer.py` before calling `map_parameters()` (recommended, see Pattern 3) | Adding a new `auto_elements` parameter to `map_parameters()` and layering `params.update(auto_elements); params.update(typst_elements)` inside it | Both are D-05-compliant (elements merge still runs last, no new precedence branching either way). The writer.py pre-merge is simpler: `map_parameters()`'s signature and body need ZERO changes beyond the allowlist entry, versus a new parameter + a second update-loop inside `map_parameters()`. Recommended for minimal surface area, but this is delegated to planner/executor discretion (CONTEXT.md explicitly leaves "how `config.language` reaches `TemplateEngine`" open) |
| Recording load-result provenance as a `self.template_source` string attribute set as a side effect of `load_template()` | Returning a small `@dataclass(frozen=True)` (`TemplateLoadResult(content: str, source: str)`) from a new method, with `load_template()`/`get_template_content()` internally unwrapping `.content` to preserve their existing `-> str` signatures | Both satisfy D-06 (single resolution walk, no duplicated priority logic) and both keep the ~5 existing `tests/test_template_engine.py` call sites + `builder.py:585` unaffected. The dataclass is marginally more type-safe (`source` values become a fixed, greppable literal set instead of a stringly-typed attribute that could silently go stale); the attribute is marginally less code. CONTEXT.md explicitly delegates this choice ("戻り値の変更か属性か小さな dataclass か") — Recommend the dataclass for the same reason Phase 26's `RawTypst`/`_ElementsEmissionKind` pattern already established in this exact module: small, explicit, greppable sentinel types over bare strings |

### Recommended Project Structure

existing flat `tests/` convention:
```

│                           # + load-result provenance (attribute or small dataclass)
```

### Pattern 1: Load-result provenance without changing `load_template()`'s public signature
**What:** Refactor `load_template()`'s priority walk into a single internal resolution routine that
records *which* priority actually resolved, as a side effect, while `load_template()` and
`get_template_content()` keep returning a plain `str` exactly as they do today — zero blast radius on
existing callers.
**When to use:** Any future "which route was actually taken" question about this same priority chain
(this phase's `lang` auto-derivation is the first consumer, but the pattern generalizes).
**Example:**
```python
# Source: this repo, template_engine.py — proposed shape, modeled on the
# existing load_template() priority walk (current lines 182-229) and the
# RawTypst/_ElementsEmissionKind sentinel-type convention Phase 26 already
# established in this exact module.

from dataclasses import dataclass


@dataclass(frozen=True)
class TemplateResolution:
    """Records WHICH of load_template()'s three priorities resolved, as a
    side effect of the SAME priority walk load_template() already performs
    -- never a second, independently-derived check (CONTEXT.md D-06 rejects
    duplicating the priority logic in a second place)."""

    content: str
    source: str  # "explicit" | "search" | "default"


class TemplateEngine:
    ...
    def resolve_template(self) -> TemplateResolution:
        if self.template_path:
            content = self._try_load_file(self.template_path)
            if content is not None:
                return TemplateResolution(content, "explicit")
            logger.warning(
                f"Custom template not found: {self.template_path}. "
                f"Falling back to default template."
            )

        if self.search_paths:
            for search_dir in self.search_paths:
                candidate_path = Path(search_dir) / self.template_name
                content = self._try_load_file(str(candidate_path))
                if content is not None:
                    logger.debug(f"Loaded template from: {candidate_path}")
                    return TemplateResolution(content, "search")

        default_path = self.get_default_template_path()
        content = self._try_load_file(default_path)
        if content is None:
            raise FileNotFoundError(
                f"Default template not found at: {default_path}. "
                f"Package installation may be corrupted."
            )
        return TemplateResolution(content, "default")

    def load_template(self) -> str:
        """UNCHANGED public contract: still returns just the content str.
        Existing callers (tests/test_template_engine.py, builder.py:585 via
        get_template_content()) are completely unaffected."""
        return self.resolve_template().content

    def get_template_content(self) -> str:
        return self.load_template()
```
**Is-default check:** `template_engine.resolve_template().source == "default"` is the exact D-06
predicate — `True` only when Priority 3 (the bundled `base.typ`) resolved, `False` for BOTH Priority 1
(explicit `typst_template`) AND Priority 2 (search-path hit, which is where the `<srcdir>/base.typ`
shadow lives) — closing the gap a declaration-based check (`typst_template is None and typst_package
is None`) leaves open.

### Pattern 2: `writer.py` calls the resolution on its OWN `TemplateEngine` instance — no new disagreement risk
**What:** `writer.py::translate()` already constructs its own `TemplateEngine` (current lines 189-197)
with `template_path`/`search_paths=[self.builder.srcdir]` — the SAME inputs `builder.py::
_write_template_file()`'s separately-constructed `TemplateEngine` (current lines 574-582) uses
(`search_paths=[self.srcdir]`, identically-computed `template_path`). Because both instances are given
identical routing-relevant inputs, calling `resolve_template()` on writer.py's instance produces the
SAME `source` verdict builder.py's instance would produce — no new cross-file duplication risk beyond
what `resolve_package_for_engine()` (WR-04) already accepts for the package/template routing decision.
**Concrete diff shape (writer.py, inside the existing master-document branch, before `map_parameters()` is called):**
```python
# Source: this repo, writer.py — proposed insertion after the existing
# TemplateEngine construction (current lines 189-197) and before the
# existing map_parameters() call (current lines 217-220).

resolution = template_engine.resolve_template()
is_default_template = resolution.source == "default"

sphinx_language = getattr(config, "language", "en")  # always a str,
                                                        # see Standard Stack
auto_lang = (
    _derive_typst_lang(sphinx_language) if is_default_template else None
)

typst_elements = getattr(config, "typst_elements", {})
effective_elements = (
    {"lang": auto_lang} if auto_lang else {}
) | typst_elements  # explicit always wins on key collision (D-05) --
                     # plain dict union, zero new branching inside
                     # map_parameters() itself.

params = template_engine.map_parameters(
    sphinx_metadata, typst_elements=effective_elements
)
```
**Note on repeated I/O:** this adds one extra template-file read per master document (the file is
small — `base.typ` is ~2KB — and this only runs for MASTER documents, since included documents return
before this code per the existing `if not is_master: ... return` early branch). `_write_template_file()`
already performs one such read per BUILD (not per document); this phase's addition performs one more
per MASTER document. For typical projects (1, occasionally a handful of nested masters — PDF-02) this
is negligible; flagged here so the plan can note it rather than treat it as a silent surprise.

### Pattern 3: `lang`-code conversion + validation helper (D-02/D-03, generic rule, no map table)
**What:** A pure function, no I/O, implementing the locked D-02 rule and D-03's warn-and-omit fallback.
**Example:**
```python
# Source: this repo, template_engine.py — proposed module-level function,
# placed near _convert_to_authors_tuple() (the existing precedent for a
# small Sphinx-metadata -> Typst-value pure conversion helper in this
# exact module).

def _derive_typst_lang(sphinx_language: str) -> str | None:
    """D-02: take everything before the first `_`/`-`/`@` separator,
    lowercase it -- a generic rule, no hand-maintained locale map. D-03:
    if the result is not 2-3 alphabetic characters, warn (naming the
    offending value) and return None so the caller omits `lang` entirely
    -- base.typ's own default ("en") then applies, and the build does not
    abort (SC#4). Examples: "ja"->"ja", "zh_CN"->"zh", "pt-BR"->"pt",
    "sr@latin"->"sr", "en"->"en", "xyz"->"xyz" (Typst itself falls back to
    English for genuinely-unknown-but-well-formed codes -- this helper
    does not need to know the set of codes Typst actually supports)."""
    import re

    head = re.split(r"[_\-@]", sphinx_language, maxsplit=1)[0].lower()
    if len(head) in (2, 3) and head.isalpha():
        return head
    logger.warning(
        f"typsphinx: could not derive a Typst 'lang' from Sphinx "
        f"'language' = {sphinx_language!r} -- omitting 'lang' (falling "
        f"back to the template's own default)."
    )
    return None
```
**Verified against CONTEXT.md's measured examples:** `"ja"`→`"ja"` ✓, `"zh_CN"`→`"zh"` ✓,
`"pt_BR"`→`"pt"` ✓, `"de"`→`"de"` ✓, and — critically — the empty-string and non-alpha cases D-03 must
catch: `""`→`re.split` yields `[""]`→`head=""`→`len(head) == 0`→ not in `(2, 3)` → **warn + omit** ✓
(never reaches Typst's own hard-fatal for an empty `lang` string, since it's never passed at all).

### Pattern 5: default-template-path judgment stays out of `builder.py` (WR-04 restated for this phase)
**What:** `builder.py::_write_template_file()` must NOT gain any `lang`-related logic. It already
constructs its own `TemplateEngine` and calls `get_template_content()` purely to write `_template.typ`
to the outdir root — it never builds a `params` dict and has no reason to know about `config.language`
at all. Confirmed by direct read (`builder.py:521-592`): the method's only config reads are
`typst_template`, `typst_package`, `typst_template_mapping`, `typst_template_function`,
`typst_package_imports`, `typst_authors` — none of which include, and none of which should be extended
to include, `language`.
**Why it matters here specifically:** it would be tempting to compute `auto_lang` once in
`_write_template_file()` (since it already resolves the template) and stash it somewhere for
`writer.py` to pick up — but that reintroduces exactly the two-components-must-agree risk WR-04 exists
to prevent, and (more concretely) `_write_template_file()` runs once PER BUILD while `config.language`
is a build-global value anyway, so there is no efficiency argument for moving the computation there;
the per-document resolution cost writer.py incurs (Pattern 2) is already bounded to master documents
only.

### Anti-Patterns to Avoid
- **Declaration-based default-template-path check** (`typst_template is None and typst_package is
  None`): misses the `<srcdir>/base.typ` shadow case entirely — explicitly rejected by CONTEXT.md D-06,
  and it is the exact failure this phase's SC#3/D-08 case ② is written to catch.
- **A second, independently-hand-written existence check for `<srcdir>/base.typ`** bolted onto the
  declaration check: duplicates `load_template()`'s priority-walk logic in a second place; drifts the
  moment `search_paths`/`template_name` rules change (CONTEXT.md D-06, explicit rejection).
- **Computing `auto_lang` inside `map_parameters()`** (reading `config.language` there, or adding a new
  `sphinx_language` parameter to `map_parameters()`): `map_parameters()` currently has NO knowledge of
  which template resolved (that information lives entirely in `TemplateEngine.resolve_template()` /
  `load_template()`, called separately) — pushing the D-06 judgment down into `map_parameters()` would
  require ALSO passing the resolution result into it, growing its signature for logic that belongs one
  layer up, in `writer.py` where the judgment naturally already needs to happen.
- **`ExtensionError`/fail-loud for an invalid/unrecognized `language` value**: explicitly rejected by
  D-03 — `language` is a Sphinx-standard config value, not a typsphinx-specific one; other Sphinx
  builders (HTML, LaTeX) do not abort on an unrecognized language value, and neither should the Typst
  builder (contrast with Phase 26 D-06's fail-loud for an unrecognized `typst_elements` *key*, which is
  typsphinx's own config surface — a different class of validation).
- **Emitting `lang: "en"` explicitly as the omit-fallback** instead of simply not adding the key to
  `params`: would create a second, drift-prone source of truth for `base.typ`'s own default value —
  explicitly rejected by D-03 for the same reason Phase 26's fontsize/papersize omission logic never
  hardcodes `base.typ`'s defaults in Python.
- **Pre-rendering `lang` to a raw Typst literal** instead of letting it flow through
  `ELEMENTS_ALLOWLIST["lang"] = STRING` → `_format_typst_value()`'s existing string branch: `lang` is
  always a short, plain alphabetic string (`"ja"`, `"de"`, ...) that needs ordinary Typst string
  quoting, exactly like `papersize` — using the `RawTypst`/RAW emission kind (fontsize's mechanism)
  here would be a category error (there is no unquoted-length form of a language code).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| Locale-code → Typst-`lang` normalization | A hand-maintained lookup table covering Sphinx's ~70 supported languages, or a BCP-47 parser dependency | The one-line D-02 split rule (`Pattern 3` above) | Locked by CONTEXT.md D-02: a generic rule needs zero maintenance as Sphinx's language list grows, and every case CONTEXT.md measured (`ja`, `zh_CN`, `pt_BR`, `sr@latin`) is covered by the single rule; a BCP-47 library would be a new runtime dependency the milestone invariant forbids |
| "Is the default template in use?" detection | A second, ad-hoc existence check against `<srcdir>/base.typ` layered onto a declaration-based check | `TemplateEngine`'s own priority-walk result (`resolve_template().source`, Pattern 1) | The declaration-based shortcut is provably wrong (misses the shadow case); a bolted-on existence check duplicates and can drift from the real resolution logic (D-06, explicit rejection) |
| CJK/multi-language Typst text rendering | Bundling CJK fonts, or a custom font-fallback layer | Nothing — out of scope (D-05, deferred). Typst's own default font resolution (system fonts) already renders CJK correctly wherever a CJK font is present; where it is not, the existing `ignore_system_fonts` CI concern is orthogonal to this phase | This phase only makes `lang` configurable; font availability is an environment concern the GATE-01 fixture strategy (D-07's `de`/Latin choice) deliberately routes around rather than solves |

**Key insight:** every piece of this phase's solution space (the conversion rule, the provenance
check, the allowlist mechanism, the fail-soft idiom) already has either a directly analogous shipped
precedent in this exact codebase (Phase 26's `RawTypst`/`ELEMENTS_ALLOWLIST`/sentinel-type pattern,
the existing `_convert_to_authors_tuple()` pure-conversion-helper shape, the existing `logger.warning`
idiom) or a locked, already-decided rule from CONTEXT.md (D-02's split rule). The research task was
locating the ONE real gap (writer.py never currently calls `load_template()` in the normal path) and
proposing a minimal-blast-radius way to close it, not inventing new mechanisms.

## Common Pitfalls

### Pitfall 1: Assuming `writer.py` already knows which template resolved
**What goes wrong:** A plan/implementation that reads `typst_template is None and typst_package is
None` (or any other declaration-based signal already visible in `writer.py::translate()` today)
instead of adding the new `resolve_template()` call reintroduces exactly the bug D-06 exists to
prevent — the `<srcdir>/base.typ` shadow case injects `lang` into a template that never declared it,
producing the `unexpected argument: lang` fatal SC#3 requires prevented.
**Why it happens:** `writer.py::translate()` currently has no code path that calls
`load_template()`/`get_template_content()`, so it is easy to assume no such call is needed and reach
for the visible (but wrong) declaration-based signal instead.
**How to avoid:** Add the explicit `resolve_template()` (or equivalent) call as its own step, and write
D-08's case ② (the `<srcdir>/base.typ` shadow, `typst_template`/`typst_package` both unset,
`language = "ja"`) FIRST as a red test before the fix lands, to prove the declaration-based shortcut
would have failed it.
**Warning signs:** A GATE-01 fixture placing an un-`lang`-declaring `base.typ` at `<srcdir>/base.typ`
(no `typst_template` config) with `language = "ja"` set aborts the build with an undeclared-kwarg
Typst fatal instead of succeeding.

### Pitfall 2: Landing the allowlist entry and the `base.typ` parameter in separate commits
**What goes wrong:** Either (a) `ELEMENTS_ALLOWLIST["lang"]` lands alone → any explicit
`typst_elements = {"lang": ...}` (which was ALREADY a valid, if previously-rejected, config prior to
this phase) now reaches `project.with(lang: ..., ...)` against a `project()` that doesn't declare
`lang` → hard Typst compile fatal for every user who had (harmlessly, before this phase) set that key
and gotten an `ExtensionError` — now gets a much less actionable downstream Typst fatal instead; or (b)
`base.typ`'s parameter lands alone → CONF-07 is a no-op (nothing ever populates `params["lang"]`).
**Why it happens:** The two edits live in different files (`template_engine.py` vs.
`templates/base.typ`) with no automated coupling between them — exactly the same shape Phase 26's
"hand-maintained 1:1 contract" comment already warns about for `papersize`/`fontsize`.
**How to avoid:** Land both in the SAME commit/task; the existing `ELEMENTS_ALLOWLIST` comment
(`template_engine.py:44-53`) already states this rule generically — this phase is a direct instance of
it, not a new risk.
**Warning signs:** `git log -p` showing `ELEMENTS_ALLOWLIST["lang"]` and the `base.typ` `lang:`
parameter added in different commits.

### Pitfall 3: Substring-matching a supplement label with an ASCII space
**What goes wrong:** An assertion like `"Abbildung 1" in full_text` (ASCII space) silently fails even
when the fix is correct, because Typst emits the supplement/number separator as **NBSP (`\xa0`)**, not
an ASCII space (measured this session during discuss, and reconfirmed this session:
`re.search(r"Abbildung\s+1", "Abbildung\xa01: cap")` → `True`; the equivalent ASCII-space literal
substring check → `False`).
**Why it happens:** Typst's `figure` supplement/counter rendering uses a non-breaking space by design
(so "Table 1" never line-wraps between the word and the number); this is invisible in an editor/terminal
and easy to author as a plain ASCII space by mistake.
**How to avoid:** Use a regex with `\s+` (Python's `\s` in a `str` pattern already matches NBSP under
the default Unicode matching mode — verified this session, no `re.UNICODE`/extra flag needed) rather
than a literal substring, e.g. `re.search(r"Abbildung\s+1", full_text)` / `re.search(r"Tabelle\s+1",
full_text)`. This is a NEW pattern for this codebase — no existing GATE-01 fixture currently performs
an NBSP-aware assertion (grep-confirmed zero hits for `xa0`/`NBSP`/`nbsp` across `tests/*.py`), so there
is no existing helper to copy; this phase's fixture is the first to need one.
**Warning signs:** A pypdf-extraction assertion that fails locally in a way that "looks like" the text
is present when printed/logged (because NBSP renders as an ordinary-looking space in most terminal
output) — always suspect the separator character before suspecting the `lang` wiring itself.

### Pitfall 4: Choosing `ja`/CJK as the PRIMARY GATE-01 supplement-language-linkage proof
**What goes wrong:** A `ja` PDF-text-extraction assertion (`"図 1"`/`"表 1"` via pypdf) can pass locally
(where CJK system fonts are present) and fail in CI (where they may not be, per the measured
`ignore_system_fonts=True` reproduction showing `\x00`-glyph/notdef output) — a flaky, environment-
dependent gate.
**Why it happens:** Typst falls back silently to a notdef/tofu glyph for characters no available font
covers, rather than failing the compile; the PDF still compiles successfully, so the flakiness only
shows up in TEXT EXTRACTION, not in `sphinx-build`'s exit code.
**How to avoid:** Follow D-07's split proof exactly — `ja` is proven via (1) a real compile succeeding
and (2) `.typ`-source inspection for the literal `lang: "ja"` string (font-independent, since it checks
the SOURCE, not rendered/extracted PDF text); the supplement-language-LINKAGE claim (i.e. "changing
`lang` actually changes what Typst renders") is proven separately via `de` (Latin script, stable across
all OS/font environments, per `pdf.py`'s `typst.compile()` call using no `ignore_system_fonts` override
— ordinary system-font resolution, which reliably has *a* Latin font everywhere).
**Warning signs:** A CI run failing only on an `ja`-language PDF-text-extraction assertion, while the
same assertion passes locally and the `.typ`-source `lang: "ja"` assertion passes everywhere — this is
the exact CJK-font-availability flakiness D-07 was written to route around, not a `lang`-wiring bug.

### Pitfall 5: Confusing `map_parameters()`'s `typst_elements` argument identity with `writer.py`'s local variable
**What goes wrong:** If the auto-derived `lang` is merged into a NEW dict but the code still passes the
ORIGINAL `typst_elements = getattr(config, "typst_elements", {})` variable (not the merged
`effective_elements`) into `map_parameters()`, the auto-derivation silently never reaches the template
at all — `lang` only ever appears when the user explicitly configured it, defeating SC#1/SC#2 entirely
while every negative/regression test (which never sets `typst_elements["lang"]`) still passes.
**Why it happens:** Easy copy-paste mistake when inserting the pre-merge step next to the existing
`typst_elements = getattr(...)` line (writer.py:215) and the existing `map_parameters(...)` call
(writer.py:218-220) — the variable NAME `typst_elements` is reused by both the original config read and
(if not renamed) the merged result, inviting a stale reference.
**How to avoid:** Name the merged dict distinctly (`effective_elements`, as in Pattern 2/3 above) and
pass THAT name into `map_parameters(typst_elements=effective_elements)` — never reuse the bare
`typst_elements` variable name for both the raw config value and the merged result.
**Warning signs:** SC#1's GATE-01 fixture (default template, `language = "ja"`, no explicit
`typst_elements`) shows `lang: "en"` (the `base.typ` default) instead of `lang: "ja"` in the emitted
`.typ` — the auto-derivation computed a value but it never reached `params`.

### Pitfall 6: NixOS sandbox — real-compile fixtures may report false negatives inside worktrees
**What goes wrong:** The new GATE-01 fixtures (real `typst.compile()`) can appear to fail for
environmental reasons unrelated to the code change.
**Why it happens:** Documented, pre-existing sandbox behavior (project memory `nixos-sandbox-test-
env.md`): `uv run <compiled-binary>` sometimes fails with a NixOS dynamic-linker error, and a
worktree's own venv can diverge from the main tree's.
**How to avoid:** Invoke `sphinx-build` as `sys.executable -m sphinx` (never `["uv", "run", "sphinx-
build", ...]`), exactly as `tests/test_typst_elements_pass_through_gate.py::_run_sphinx_build()`
already does; per-worktree provisioning (`env -u VIRTUAL_ENV -u UV_PROJECT_ENVIRONMENT uv sync --extra
dev` + `uv run pytest`) per CLAUDE.md's mandatory worktree-isolated execution protocol.
**Warning signs:** `typst` import failure inside a worktree despite `typst==0.15.0` being present on
the main tree.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|----------------------|
| A pathological `language` value (extremely long string, control characters) reaching `typst.compile()` via a malformed but accidentally-2-3-alpha-passing derived `lang` | Denial of Service | Not realistically reachable: the D-02 split rule takes only the substring before the first `_`/`-`/`@` and the D-03 validation requires the RESULT to be exactly 2-3 alphabetic characters — a pathologically long or control-character-laden `language` value simply fails the `len(head) in (2, 3) and head.isalpha()` check and is warned-and-omitted, never reaching Typst at all |
