## Item 1 — SC#9's second repository: `typsphinx-doc-translations`

**What is owed:** the same `lang` workaround plan 45.1-03 removed from `docs/source/conf.py` (the
hand-rolled `derive_typst_lang` import plus manual `typst_elements["lang"]` reconstruction) also
exists in the separate `typsphinx-doc-translations` repository's own `conf.py`. CONF-12/D-I makes it
removable there too — `TemplateEngine.uses_bundled_default_template()` is narrowed to the
`typst_package` guard alone, so the extension itself now auto-derives `lang` on that repository's
explicit `typst_template` route, exactly as it now does in this repository.

**To whom:** the `typsphinx-doc-translations` repository's own maintainer/next editor, at that
repository's own next update against a typsphinx release carrying CONF-12 (v0.7.1 and later).

**Why it is now safe:** identical reasoning to `docs/source/conf.py`'s own removal
(`45.1-GATE-EVIDENCE-03.md`, Task 3 appendix) — the auto-derived `lang` value is byte-identical to
what the hand-rolled workaround produced, only its provenance changes (extension-side derivation
instead of `conf.py`-side reconstruction).

**What evidence closes it:** the same shape of proof plan 45.1-03 recorded here — a real
`sphinx-build`/`tox`-equivalent build in that repository, before and after the workaround's removal,
with the emitted `lang:` value shown byte-identical across both.

**Out-of-phase scope:** SC#9 explicitly scopes this to a handoff item, not in-phase work — that
repository is outside this one's tree. This rides alongside the standing second-repository tagging
cost every release of this project already pays (every release tags **two** repositories — the
parent and `typsphinx-doc-translations` — a standing cost since v0.6.4).

**Sharper consequence, flagged explicitly:** CONF-12 is not purely additive for that repository.
Its own custom template (if it declares fewer than the nine published parameters and omits `lang`)
must add a `lang` parameter to its `#let project(...)` signature **before its next build** against a
typsphinx carrying CONF-12 — otherwise that build fails with `TypstError: unexpected argument: lang`,
the exact class of failure T-45.1-05 (this phase's own threat register) named as the transferred
cost of widening `lang` derivation. This is the same fix `examples/charged-ieee/approach2`'s
shipped template needed in-repository (plan 45.1-03's Deviation 1) — verify that repository's own
custom template(s) declare `lang` before merging a typsphinx version bump there.

## Closing — deferred items restated (from `45.1-CONTEXT.md` `<deferred>`)

So the next reader does not have to re-derive these from `CONTEXT.md`:

1. **The `..args` argument sink in `templates/base.typ`, plus a documented convention.** Measured
   to compile (`#let project(title: "", ..args, body)`, the sink may precede the trailing
   positional `body`). Rejected for this phase on three grounds: it would silently swallow typos in
   `typst_template_function["params"]`, reversing the fail-loud stance `ELEMENTS_ALLOWLIST` already
   takes; it would hide the contract mismatch this phase exists to resolve rather than resolving
   it; and it would weaken SC#4's constraint (that adding a parameter is a deliberate, visible
   decision). **Kept as the option of record** if a future phase needs to add a tenth parameter
   without breaking every correctly-written custom template that declares exactly today's nine.

2. **The declined lockstep sync test, and the unguarded fourth lockstep site.** D-J rejected
   building a structural sync test over the contract's surfaces (`templates/base.typ`,
   `templates.rst`, `docs/source/_typst/custom_template.typ`, the emission sites), even though
   `tests/test_preview_version_sync.py` is an established precedent for exactly that shape.
   `docs/source/_typst/custom_template.typ` therefore **remains the unguarded fourth lockstep site**
   the v0.6.4 review first flagged — a future parameter addition (or removal) must remember to
   update it by hand; nothing will fail loudly if someone forgets.

3. **The `typst_authors` migration path for existing users.** CONF-10/D-F removed the config value
   outright; `configuration.rst`'s Author Information section (plan 45.1-05) documents the
   surviving `typst_template_function["params"]["authors"]` route and its precedence, but **where a
   dedicated migration guide (a standalone "Migrating from typst_authors" note, a CHANGELOG-linked
   upgrade guide, or nothing beyond the rewritten reference page) lives was left to planning and was
   not decided in this plan.** This is an open question for whoever writes the CHANGELOG entry
   (Item 2 above) or a future documentation pass to resolve, not a defect in this phase's own scope.
