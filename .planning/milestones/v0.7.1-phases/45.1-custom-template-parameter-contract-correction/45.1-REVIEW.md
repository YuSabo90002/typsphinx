## Summary

This phase corrected the published custom-template parameter contract (D-A/D-B/D-D/D-I/D-F, etc.) and added a large, well-constructed suite of real-compile regression gates and a docs-vs-code prose agreement guard (`test_docs_contract_claims_gate.py`). I traced the core logic paths in `template_engine.py` (`resolve_template`, `uses_bundled_default_template`, `map_parameters`, `render`), `writer.py` (`_resolve_entry_element`, `translate`), and `builder.py` (`_write_template_file`, `_resolve_output_stem`) against the documented contract and against every fixture/test in scope, and traced the docs prose in `configuration.rst`/`templates.rst`/`advanced.rst` against `TemplateEngine.uses_bundled_default_template()`'s actual predicate by hand-simulating the new `test_docs_contract_claims_gate.py` classifier over the current doc text. The production logic, the new regression gates, and the fixtures are internally consistent with each other and with the documented contract (D-B's exclusive-params branch, D-I's widened `lang` derivation, D-F's removal of `typst_authors`, CONF-09's `_resolve_entry_element` precedence).

I did not find any BLOCKER-class defect in the production code paths this phase touched. I found two WARNING-level issues -- one a real, user-visible content defect in a shipped, "Recommended" example that this phase's own file touches failed to catch, the other a dead/misleading constant in the new prose-agreement test module -- and one INFO-level robustness note about that same test module's classifier.

## Warnings

### WR-01: `examples/charged-ieee/approach1` ("Recommended" approach) never passes a title to the compiled paper

**File:** `examples/charged-ieee/approach1/conf.py` (and mirrored in `examples/charged-ieee/README.md:30-52`, and in the introductory code sample of `docs/source/user_guide/templates.rst:38-51`, "Configuration-Based Templates")

**Issue:** `approach1/conf.py` sets `typst_package` alone (no `typst_template`) and declares `typst_template_function["params"]` with exactly four keys -- `abstract`, `index-terms`, `paper-size`, `authors` -- and no `typst_template_mapping`. Under this phase's own D-B rule (`TemplateEngine.render()`, `typst_template_params_specified` branch), a declared `params` dict is the **complete, exclusive** parameter set: `all_params = dict(self.typst_template_params)` entirely replaces the auto-derived set, and on the package route `map_parameters()`'s title/authors/date back-fill is *also* gated off by `if not self.typst_package:` (so even the auto-derived fallback that would otherwise supply `title: ""` never runs). Since `params` never names `title`, and no `typst_template_mapping` routes anything to it, the emitted `#show: ieee.with(...)` call carries **no `title` argument at all** -- even though the file defines `project = "Machine Learning Applications in Computer Vision"` and reuses it for `typst_documents`. The compiled "recommended" example paper therefore has no title in the PDF; `ieee()`'s own bare default applies.

I verified via `git log -p` that `title` was never present in this file's `params` dict, in any commit -- this is not a regression *introduced* by this phase's D-B/D-F changes (the package-route back-fill was already gated off `typst_package` before 45.1), but this phase directly touched this exact file (`d5277d0`, migrating the removed `typst_authors` value onto the `params` route) and re-verified its parameter completeness without catching the missing `title`. `tests/test_examples_charged_ieee_gate.py::test_approach1_package_alone_sample_builds_and_compiles` asserts `authors:`, `John Doe`, `department:`, etc. are present in the show-rule region, but never asserts the project title (or any `title:` argument) appears anywhere -- so this gap is currently invisible to the test suite. Notably, `docs/source/user_guide/configuration.rst`'s own "Complete Example" (which *does* declare `"title": project` inside `params`) and `docs/source/examples/advanced.rst`'s charged-ieee sample (same) show the correct pattern, and `templates.rst` itself documents exactly this failure mode as a "silent trap" in its own `.. warning::` block under "Custom Parameters" -- the shipped `approach1` example, and the introductory code sample earlier in the very same `templates.rst` page, fall into that documented trap themselves.

**Fix:** Add `"title": project` to `typst_template_function["params"]` in `examples/charged-ieee/approach1/conf.py` and to the matching snippet in `examples/charged-ieee/README.md`; consider adding `"title": "..."` to `templates.rst`'s "Configuration-Based Templates" introductory sample too, for consistency with `configuration.rst`'s Complete Example. Add an assertion in `test_examples_charged_ieee_gate.py::test_approach1_package_alone_sample_builds_and_compiles` that the project title (or a `title:` argument) actually reaches the show-rule region, so this class of gap cannot recur silently.

### WR-02: `WITHHOLDING_TOKENS` in the new docs-contract classifier is defined but never consulted

**File:** `tests/test_docs_contract_claims_gate.py:185-193`

**Issue:** `WITHHOLDING_TOKENS = ("withheld", "never", "except", "does not apply", "do not apply", "not apply", "only when")` is introduced with the comment "the vocabulary this docs corpus uses to deny a route", implying `_classify_sentence()` (the function whose correctness the whole module's two-way agreement proof rests on) draws on this vocabulary. It does not: `_classify_sentence()` (lines 232-288) instead hardcodes three independent regexes matching the literal substrings `"except"`, `"does not apply"`/`"not apply"`, and `"withheld"` directly -- `WITHHOLDING_TOKENS` itself is never referenced anywhere else in the file (confirmed via `grep -n WITHHOLDING_TOKENS`, one hit: the definition). Two of its seven entries (`"never"`, `"only when"`) are not wired into the classifier's withholding logic at all, despite being named as vocabulary the classifier should recognize. In the current doc corpus this happens not to matter (`configuration.rst`'s "Scope: every non-package route" paragraph, the only route-scope-claim chunk that currently matters, is decided entirely by the `except`/`withheld` regexes and never depends on `"never"`/`"only when"`), but the constant is misleading to a future maintainer who edits this module expecting `WITHHOLDING_TOKENS` to be load-bearing, and is dead code as written.

**Fix:** Either wire `WITHHOLDING_TOKENS` into `_classify_sentence()`'s matching (e.g. iterate the tuple instead of three separate hardcoded regexes), or delete the unused constant and its now-inaccurate docstring comment so the module's actual (narrower) matching vocabulary is what the code states.

## Info

### IN-01: `_classify_sentence()`'s "does not apply" branch captures to end-of-chunk with `re.DOTALL`, not just the nearby clause

**File:** `tests/test_docs_contract_claims_gate.py:265-271`

**Issue:** `not_apply_match = re.search(r"(?:does\s+\*{0,2}not\*{0,2}\s+apply|not\s+apply)\b(.*)", lowered, re.DOTALL)` captures everything from the matched phrase to the end of the whole chunk (a full paragraph, in `_claim_sentences()`'s blank-line-delimited unit) and treats every route token found anywhere in that remainder as withheld. This is deliberately what makes the `PRE_FIX_FALSE_CLAIM` RED-proof in `TestForbiddenClaimDetectorIsFailFirst` work (that historical sentence enumerates its withheld routes at length after the marker), and the current live doc corpus never triggers this branch at all (no page currently contains the phrase "not apply"/"does not apply"), so this is not exploitable today. It is a latent fragility, though: if a future doc edit adds a paragraph containing "...does not apply to X, but Y is still affirmed elsewhere in this same paragraph", the unbounded capture would misclassify Y as withheld too, silently failing `test_docs_withheld_routes_equal_code_withheld_routes`/`test_docs_affirmed_routes_equal_code_affirmed_routes` for an unrelated reason.

**Fix:** No action required now given the branch is unused by the live corpus, but consider bounding this capture the same way the `except`/`withheld` branches already are (a short window to the next comma/colon/period, per this function's own docstring convention) the next time this module is touched, so its three withholding branches behave uniformly.
