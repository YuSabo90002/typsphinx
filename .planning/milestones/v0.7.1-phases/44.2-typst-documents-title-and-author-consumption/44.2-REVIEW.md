## Summary

This is round 4 of the `typst_authors`/entry-title-author precedence work. The runtime mechanism
— `_resolve_entry_element()` in `writer.py` and the reordered seed/mapping-loop logic in
`TemplateEngine.map_parameters()` — is unchanged from round 3 and remains sound: traced against
`git diff cf48c3a..HEAD`, every write site that can determine the emitted `authors` is exactly the
nine sites `tests/test_authors_pipeline_stage_gate.py`'s AST enumeration expects, and the D-05
comment in `template_engine.py` accurately states the target-key rule. All 156 tests across the
in-scope test modules pass (`test_authors_pipeline_stage_gate.py`,
`test_entry_metadata_precedence.py`, `test_entry_metadata_route_uniformity.py`,
`test_params_authors_writers.py`, `test_config_template_mapping.py`, `test_template_engine.py`),
plus the two real-compile gates in `test_document_metadata_render_gate.py` and
`test_multi_master_metadata_no_leak.py` (8/8). `ruff`/`mypy` are clean on both source files.

**CR-01 from round 3 (`configuration.rst`'s "and nothing else in typsphinx replaces it" false
universal claim) is fixed.** Commits `f5d79d4` and `b036e65` rewrote the Precedence block as an
explicit two-stage rule (stage 1 = the parameter mapping inside `map_parameters()`, stage 2 =
`typst_template_function`'s dict-form `params` applied in `render()`), and every negative/universal
claim I traced is now correctly scoped to the stage it quantifies over — including the two
Precedence-block bullets that round 4 itself found and fixed (the `{"author": "doc_authors"}` and
`{"project": "authors"}` illustrations previously read as claims about the *final* rendered output;
they now say "Stage 1's own output ... subject to stage 2's override" and are pinned by a new drift
guard, `test_configuration_rst_stage1_bullets_name_stage2_override_explicitly`). I independently
re-derived the two-stage rule from the code (`map_parameters()`'s seed-then-mapping-loop order, and
`render()`'s `all_params.update(params)` then `all_params.update(self.typst_template_params)` merge
order) and it matches the published prose at every point I checked, including the edge cases the
prior three rounds got wrong (a non-`"author"` source routed to `"authors"`, and an `"author"`
source routed away from `"authors"`). The "Typst Documents" item-4 summary sentence ("this value
also beats `typst_authors`... by exactly one thing") is narrower than it first reads, but is
accurate as literally stated once "this value" is read as *the entry's own author value* — that
value can only reach the `authors` template parameter via an `"author"` → `"authors"` mapping
entry, which is exactly the condition the sentence names; the immediately following forward
reference to `Author Information`_ for "the two cases this summary does not cover" resolves what
otherwise reads as a contradiction.

`tests/test_authors_pipeline_stage_gate.py`'s assertions are not tautological: the frozen
`EXPECTED_STAGE_SITES`/`REACHABLE_STAGE_KNOBS`/`UNREACHABLE_STAGE_PROOFS` declarations are
hand-written (never derived by calling the AST walker and pasting its own output), the two
`sphinx-build` gates (`test_three_knob_build_emits_template_function_authors_not_the_seed` and its
attribution control) exercise a real build end-to-end, and `test_render_applies_template_function_

observable effect. I mentally transposed `render()`'s two `update()` calls and confirmed that would

## Warnings

### WR-01: `effective_elements` merge still crashes with an unhandled `TypeError` on a non-`dict` `typst_elements`

**File:** `typsphinx/writer.py:319-321`

**Issue:**

```python
effective_elements = ({"lang": auto_lang} if auto_lang else {}) | (
    typst_elements or {}
)
```

Re-assessed on its own merits rather than inherited from the prior round's classification.
`typst_elements` is registered via `add_config_value("typst_elements", {}, "html", [dict])`
(`typsphinx/__init__.py:48`); Sphinx's `add_config_value` type declaration only **warns** on a
mismatch, it does not coerce or reject the value. If a user sets `typst_elements` to any non-`dict`
*truthy* value (a list, a string, a tuple — a plausible conf.py typo, e.g. copying the
`typst_template_assets` list-of-strings shape by mistake), `typst_elements or {}` evaluates to that
truthy non-dict value (the `or {}` guard only fires on falsy values), and `dict | <non-dict>` raises
`TypeError: unsupported operand type(s) for |`. This crashes `TypstWriter.translate()` with an
unhandled Python traceback for **every** master document in the build, rather than the descriptive
`sphinx.errors.ExtensionError` this codebase otherwise uses for bad `typst_elements` input (compare
`map_parameters()`'s own `ExtensionError` for an unknown `typst_elements` key, three lines away in
the call graph).

This code is unchanged by phase 44.2 (`git diff cf48c3a..HEAD -- typsphinx/writer.py` does not touch
these lines; the block predates this phase, introduced in phase 27.1's CONF-07 work) and is not part
of CONF-09's title/author consumption logic. It is included here because `writer.py` is an in-scope
file for this review and the finding has now been carried, unfixed, across two consecutive review
rounds (documented previously at the identical location in the round-3 `44.2-REVIEW.md`).

**Fix:** Normalize on type, not truthiness, before the merge:

```python
if typst_elements is not None and not isinstance(typst_elements, dict):
    logger.warning(
        f"typsphinx: typst_elements must be a dict, got "
        f"{type(typst_elements).__name__} -- ignoring it for this document."
    )
    typst_elements = {}

effective_elements = ({"lang": auto_lang} if auto_lang else {}) | (typst_elements or {})
```

### IN-01: `test_invalid_mapping_type` never calls `app.build()` and asserts nothing

**File:** `tests/test_config_template_mapping.py:165-186`

**Issue:**

```python
def test_invalid_mapping_type(make_app, tmp_path):
    """Test that invalid mapping type is handled gracefully"""
    ...
    # Should not crash, but may emit warning
    app = make_app(srcdir=srcdir)
    # Build should complete even with invalid config
    # (implementation should validate and fallback to default)
```

The docstring and trailing comments describe a build-time contract ("Build should complete even
with invalid config", "may emit warning", "should validate and fallback to default"), but the test
body never calls `app.build()` — `make_app()` only constructs the `Sphinx` application object, it
does not run the write phase, so `TypstWriter.translate()` / `TemplateEngine.map_parameters()` are
never reached and the `typst_template_mapping = ['invalid', 'list']` misconfiguration this test
exists to exercise is never touched. The test currently passes purely because app construction
alone cannot fail on this config value, regardless of whether the described "handled gracefully"
behavior is true. It is not: `map_parameters()`'s mapping loop does
`for sphinx_key, template_key in self.parameter_mapping.items():`, and a `list` has no `.items()`
method — a real `-b typst` build with this exact `conf.py` raises `AttributeError` inside the write
phase, not the graceful degrade-to-default the docstring claims. This predates phase 44.2 and is
untouched by its diff (`git diff cf48c3a..HEAD` does not modify this test), but the file is fully
in this phase's review scope.

**Fix:** Either call `app.build()` and assert the actually-observed behavior, or convert the
trailing comments into a real assertion:

```python
app = make_app(srcdir=srcdir)
with pytest.raises(Exception):  # currently AttributeError; tighten once triaged
    app.build()
```

or, if graceful degradation is the intended contract, fix `TemplateEngine.__init__`/
`map_parameters()` to validate the mapping's type and fall back, then assert on the emitted `.typ`
content.
