# Phase 54.1: Code Review Report

**Reviewed:** 2026-08-16T03:20:51Z
**Depth:** standard
**Files Reviewed:** 27
**Status:** issues_found

## Summary

Phase 54.1 adds three pre-write refusal checks to `TypstBuilder._validate_used_template_paths()`
(templates_path collision / hoisted CONF-17 / reserved-key case collision), a shared
`_conf17_violation_message()` builder, and a symmetric containment predicate `_paths_related()`,
then retires the `_templates/`-as-Typst-template documentation pattern across `docs/`, `README.md`
and `examples/`, pinned by a repo-wide grep gate.

I traced `_paths_related()` and `_validate_used_template_paths()` line-by-line against the
`_copy_used_template_bundles()` sibling logic they duplicate (D-06), re-derived the ordering/
aggregation guarantee by hand against the mixed-failure-kind fixtures, and ran every listed test
file plus a synthetic reproduction. All 29 tests in the listed files pass (27 in the core gate
files + 2 in the examples gate); the diff to `typsphinx/builder.py` is purely additive except for
the expected extraction of `_conf17_violation_message()` from the pre-existing `finish()`-side
guard, confirmed byte-identical against the deleted inline text via `git diff`.

No BLOCKER-class defect found. The path-relation logic is symmetric, case-folded consistently with
the codebase's established `_collision_key()` convention, and the "no `.typ` file survives a
refusal" and "one aggregated, `sorted()`-ordered `ExtensionError`" guarantees both hold under
direct testing, including across inverted declaration order and mixed failure kinds. I did find one
concrete, reproduced quality regression (WR-01) — the new pre-write pass makes an existing
template-not-found warning fire a third time for one specific misconfiguration shape — and one
real, but already-documented, correctness gap (WR-02) worth a second pair of eyes: the
`templates_path` resolution root the phase's docstring itself flags as unhandled.

## Warnings

### WR-01: Pre-write validation triples an existing "Custom template not found" warning

**File:** `typsphinx/builder.py:1181` (the `template_engine.resolve_template()` call inside
`_validate_used_template_paths()`)

**Issue:** `_validate_used_template_paths()` now unconditionally calls
`TemplateEngine.resolve_template()` for every used registry key (needed for the CONF-17 hoist,
per the method's own docstring at builder.py:1012-1023). `resolve_template()`
(`typsphinx/template_engine.py:372-375`) emits `logger.warning("Custom template not found: ...
Falling back to default template.")` whenever an explicit `template_path` was configured but the
file does not exist on disk. Before this phase, that resolution ran twice per build for the
synthesized built-in `"typst"` key misconfigured this way: once in `writer.py`'s
`render_wrapper()` (write time) and once in `_copy_used_template_bundles()` (finish time). This
phase adds a third call site with no de-duplication, so the identical warning now appears three
times in one build's log output instead of two.

Reproduced directly against the current tree (not the pre-fix tree) with a minimal fixture setting
`typst_template = "does_not_exist.typ"` (no `typst_documents`, so the checked key set comes from
the synthesized default entry):

```
$ python -m sphinx -b typst src build
...
Custom template not found: .../does_not_exist.typ. Falling back to default template.
preparing documents... done
writing output... [index]Custom template not found: .../does_not_exist.typ. Falling back to default template.
 done
typst: wrote 1 wrapper file(s) -- compile these: index.typ
Custom template not found: .../does_not_exist.typ. Falling back to default template.
build succeeded.
```

Three identical warnings for one misconfiguration. This is narrow in scope — it only reaches a
key whose `template` value is an explicit path that does not exist, which is possible only for
the *synthesized* `"typst"` key (a `typst_document_templates`-declared key with a nonexistent
`template` is already rejected earlier by `resolve_template_registry()`'s D-08 existence check,
so `_validate_used_template_paths()` never reaches `resolve_template()` for a declared key in this
state) — but it is a real, user-visible log-noise regression this phase introduces, not a
pre-existing condition it merely inherits.

**Fix:** Either suppress the warning on this call site specifically (e.g. a `logging.disable`-style
guard, or a `TemplateEngine.resolve_template(warn=False)` parameter used only by the validator),
or accept the noise but note it in the phase's CHANGELOG entry alongside the other documented
consequences of the new pre-write pass — right now it is undocumented.

### WR-02: `templates_path` is resolved against `srcdir`, not `confdir`, contradicting Sphinx's own documented semantics for that config value

**File:** `typsphinx/builder.py:1107-1114`, `typsphinx/builder.py:1047-1051` (docstring)

**Issue:** `_validate_used_template_paths()` resolves every `templates_path` entry via
`path.join(str(self.srcdir), raw_entry)`. Sphinx's own documentation for `templates_path` states
relative entries are taken as relative to *the configuration directory* (`confdir`), not `srcdir`
— they coincide in the overwhelmingly common case (no `-c`/`--confdir` override), but are not
guaranteed to. The method's own docstring at builder.py:1047-1051 acknowledges this precisely:
*"A project using Sphinx's separate `-c` confdir option is NOT covered by this method ...
this method never reads `self.confdir`."*

Because this is self-documented as a known limitation rather than an oversight, I am not raising
it as a BLOCKER, but the phase's stated goal is closing a *security-relevant* republication hole
(WR-01 upstream), and an unresolved `confdir`≠`srcdir` project gets a false sense of safety: the
build succeeds silently with a `templates_path` collision that the wholesale bundle copy at
`finish()` will still walk into, since `_copy_used_template_bundles()` has no `templates_path`
awareness of its own either. The gap is real, not hypothetical — Sphinx's `-c` flag is a supported,
documented option, and this phase's own `CHANGELOG.md` entry describes the fix in absolute terms
("template layout is now validated before anything is written") without mentioning this carve-out.

**Fix:** At minimum, mention the `-c`/confdir carve-out in the CHANGELOG's new breaking-change
entry so a `-c`-using project owner knows this new safety net does not cover their layout. If
closing it outright is in scope, resolve `templates_path` entries against `self.confdir` (Sphinx
exposes this on the app/config where reachable from a `Builder`) instead of `self.srcdir`.

## Info

### IN-01: `_paths_related()` does not resolve symlinks before comparing paths

**File:** `typsphinx/builder.py:215-223`

**Issue:** `_paths_related()` normalizes both operands with
`path.normpath(path.abspath(path_a))` — `abspath()` does not resolve symlinks (unlike
`os.path.realpath()`). If a project's `templates_path` entry and a used template's resolved
bundle directory are the *same physical directory* reached through two different symlinked paths
(e.g. one operand traverses a symlinked `docs/` mount), the containment test would report "not
related" and the collision would go undetected — a false negative in exactly the class of hazard
this phase closes. This is a narrow, unlikely-to-be-hit edge case (it requires a symlink inside
the project tree pointing at another part of the same tree), and is consistent with how the rest
of this module already treats paths (`_collision_key()`, `_violates_conf17()` — neither resolves
symlinks either), so I am not asking for a design change, just flagging it as an unstated
assumption worth a one-line docstring note alongside the existing "neither path is guaranteed to
exist on disk" comment.

**Fix:** Optional: add a sentence to `_paths_related()`'s docstring noting symlinks are not
resolved, matching the project's existing non-normalization disclosures (case-folding, Unicode
NFC/NFD) elsewhere in this file.

### IN-02: Example tree diagrams describe an `_templates/` directory that does not exist on disk

**File:** `examples/advanced/README.md:20`, `examples/advanced/index.rst:85-86`

**Issue:** Both files' project-structure diagrams now show, alongside the real `_typst/`
directory:
```
├── _templates/             # Sphinx's own templates_path override directory (HTML theme; empty here)
```
`examples/advanced/conf.py` does set `templates_path = ["_templates"]` (line 24), but no
`examples/advanced/_templates/` directory actually exists on disk (confirmed: `ls
examples/advanced/` shows only `_typst/`, `chapter1.rst`, `chapter2.rst`, `conf.py`, `index.rst`,
`README.md`). Sphinx tolerates a missing `templates_path` entry at build time (verified: the
example still builds), so this is not a functional defect, but the tree diagram presents an
"(empty here)" directory as if it exists on disk when it does not — a reader who goes looking for
it to understand the two-directory split this phase intentionally documents will not find it.

**Fix:** Either create an empty `examples/advanced/_templates/` (with a `.gitkeep` or a short
`README` explaining it is intentionally unused), or reword the diagram/comment to say the
directory is *not present* rather than *empty here* — the current wording overstates what is on
disk.
