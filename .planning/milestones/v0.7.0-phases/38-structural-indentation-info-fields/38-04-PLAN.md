**Section: migration strategy (D-14).** D-14 leaves the strategy to Claude under one non-negotiable
constraint — hand-derived expected strings plus a recorded census, never regeneration from the new
code's output. Write the strategy down explicitly:

- Migration is owned **per plan, at the point the bytes change** (milestone invariant #5), not deferred
  to a single closing pass. Each of 38-05, 38-06 and 38-07 migrates the Bucket A rows assigned to it,
  in the same commit that changes the bytes, so each commit's whole-suite delta is a set difference
  with a stated cause rather than a mixed bag.
- The `golden.typ` byte-identity gate is migrated by applying the contract's rules to the EXISTING
  golden by hand — inserting the body wrapper's opening and closing tokens at the positions §2
  specifies — and only then rebuilding to confirm. If the rebuilt output and the hand-derived golden
  disagree, the diff is investigated and either the code or the contract is wrong; the golden is never
  replaced with the build's output. Record this rule in the census so the executor of 38-05 cannot
  reasonably read it any other way.
- Page counts are re-measured, not re-derived, and live in Bucket D. Every commit that moves one states
  the measured before and after and the reason.
- If an unpredicted file breaks, it is migrated by the plan that broke it and the census records the
  miss at closeout rather than being silently amended — the Phase 37 convention that a census which was
  wrong in a recorded way is more useful than one silently corrected.

**Section: whole-suite baseline.** Run `uv run pytest -m "not slow" -q` on the current tree and record
