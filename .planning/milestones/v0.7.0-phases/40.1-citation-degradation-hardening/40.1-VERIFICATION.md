### Known Finding (from `40.1-REVIEW.md`) — judged, not re-derived

`40.1-REVIEW.md` records one WARNING: `_reference_anchor_decision`/`_resolve_xref_docname` runs twice
per citing reference that has both a `refuri` and a paired citation `backrefs` entry (once from
`visit_reference`, once from `visit_citation`'s backref loop). The regression test with the matching
name/docstring (`test_wr03_xref_resolution_happens_once_per_reference`) does not reach this path
because its own fixture carries no paired citation.

**Judgement:** this does not undermine ROADMAP SC#3. SC#3's contract is that the D-14 eligibility
*judgement* is derived in exactly one place so the two call sites cannot silently *disagree* — it is
not a claim that the predicate is invoked exactly once per document. Both call sites call the *same*
pure function on the *same* node and therefore necessarily agree (verified: the predicate has no
hidden state and the warning fires exactly once, confirmed by the passing
`test_wr03_xref_resolution_happens_once_per_reference`, even though that test's own topology doesn't
reach the double-invocation case). The double-call is a latent DRY/perf note that becomes a real risk
only if a *future* change adds a side effect to the predicate (e.g. moving the degrade-warning inside
it) — at that point the existing test's coverage gap would let a real regression through. It is
correctly filed as WARNING (not BLOCKER) by the code review, is not a defect in currently-shipped
behavior, and does not affect SC#1, SC#2, SC#4, or SC#5. No gap is recorded for it here; it is a
pre-existing, already-documented, accepted residual worth carrying to Phase 41 or later as a
test-coverage note, not a phase-blocking issue.
